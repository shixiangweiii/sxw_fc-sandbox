## 3. 评审发现

严重度的含义：**高** = 某些合理的配置或部署下会出现错误行为或安全问题；**中** = 并发、故障或生产环境下会出现错误或资源问题；**低** = 可维护性、效率或测试脚本问题。

### 高

**H1　`min_hot` 保留的运行中沙箱约 3 分钟后会被平台回收**
- 位置：`sandbox_pool/core/maintainer.py:184`（创建时的平台超时）；READY 状态的沙箱没有任何续期逻辑。
- 问题：开启暂停时，沙箱创建时的平台超时是 `idle_pause_after_s + idle_platform_extra_s`（默认 180s）。由 `min_hot` 保留、故意不暂停的 READY 沙箱永远不会调用 `set_timeout`。
- 影响：`min_hot=2` 时，这 2 个沙箱约 180s 后被平台销毁，但库里仍是 READY。下次借用时 `set_timeout` 失败，借用失败并销毁沙箱，然后重新补货，每 3 分钟循环一次，「热沙箱」完全起不到作用。默认 `min_hot=0` 不会触发。
- 建议：维护循环定期给 READY 沙箱续期（例如剩余时间 < 一半时 `set_timeout`）；或者对 READY 沙箱不设短超时，只在暂停前兜底。补一个 `min_hot > 0` 且运行超过平台超时的测试。

**H2　`GET /v1/sandboxes` 暴露了 `lease_id`，而接口没有鉴权**
- 位置：`sandbox_pool/api/routes.py:88-90`；整个 API 没有鉴权。
- 问题：`lease_id` 是调用 run_code / commands / files / 归还的唯一凭证，调试接口原样返回库里的行（包含 `lease_id`、`provider_id`）。
- 影响：任何能访问服务的人都可以读到别人的 `lease_id`，然后在别人的沙箱里执行任意代码、读取文件，或者直接归还导致对方的沙箱被销毁。demo 仅内网使用可以接受，**对外暴露前必须处理**。
- 建议：调试接口去掉 `lease_id` 或只对管理员开放；API 增加调用方鉴权（API Key / mTLS / 网关），借用绑定调用方身份。

### 中

**M1　排队请求在抢沙箱期间不刷新心跳，健康的沙箱可能被误销毁**
- 位置：`sandbox_pool/core/allocator.py:79-89`。
- 问题：队首请求执行 `_try_claim()` 期间不刷新心跳。这一步最多尝试 10 次，每次都可能要恢复一个暂停的沙箱（实测约 2.3～3.1s）。其他副本的 `expire_waiters` 发现心跳超过 5s 没更新，就会把这个请求置为 TIMEOUT；超过 deadline 时也一样。
- 影响：恢复失败后换下一个重试、或者数据库慢的时候，抢到的沙箱在 `cas_waiter → GRANTED` 这一步失败，随后被 `end_lease(FAILED)` 销毁，客户端收到 504。一个健康、刚恢复的沙箱就这样被白白销毁了。
- 建议：抢沙箱前后都刷新心跳，或者把心跳超时设为明显大于「最大尝试次数 × 恢复耗时」；超过 deadline 时优先把已经拿到的沙箱交给请求方，而不是销毁。

**M2　借用到期回收时没有再次检查到期时间，可能覆盖刚刚成功的续期**
- 位置：`sandbox_pool/core/maintainer.py:90-93`，`sandbox_pool/core/lifecycle.py:96`。
- 问题：`expire_leases` 先列出已到期的借用，然后 `end_lease` 只按 `state=ACTIVE` 做 CAS，没有带上 `expires_at <= now` 条件。
- 影响：客户端在借用快到期时续期，续期已经成功返回 200，但同一时刻维护循环仍按旧的到期时间把借用改成 EXPIRED 并销毁沙箱。之后客户端的调用都返回 409，解释器状态全部丢失。概率低，但一旦发生就是数据丢失。
- 建议：`cas_lease` 在 EXPIRED 路径上加 `expires_at <= now` 条件（仓储层已经有 `expect_unexpired_at` 这种写法，可以补一个反向条件）。

**M3　续期时平台超时设置失败会返回 500，且库和平台记录的到期时间不一致**
- 位置：`sandbox_pool/core/allocator.py:204-215`。
- 问题：续期先把新的 `expires_at` 写进库，再调用 `provider.set_timeout`。只处理了 `SandboxNotFound`，其他异常（网络、5xx）直接冒泡成 500。
- 影响：库里认为借用还有 10 分钟，平台上沙箱仍按旧时间 + 60s 到期被回收。之后调用方拿到的是笼统的 502，要等对账（60s 以上）才会清理掉这条记录。
- 建议：先调用 `set_timeout`，成功后再写库；或者失败时把 `expires_at` 回滚，并返回 502 / 可重试的错误。

**M4　副本在归还后崩溃，会占住容量约 `op_timeout` 秒**
- 位置：`sandbox_pool/core/lifecycle.py:110`（归还时销毁在后台执行）；过渡态统一使用 `op_timeout_s`。
- 问题：归还接口先返回，再在后台销毁沙箱。副本在这之间崩溃，DESTROYING 记录要等 `op_deadline` 过后才会被接管。**端到端测试实际观察到**：5 个容量被占住 70s（按 `op_timeout=60` 配置；默认 120s 时会更久），期间只能排队。
- 建议：按操作类型设置不同的截止时间（DESTROYING / RESUMING 可以设为 15～30s）；或者先销毁再返回（销毁 p99 只有 0.39s，代价很小）。

**M5　SQLite 下所有读操作也拿写锁，进程内只有一个连接，吞吐上限低**
- 位置：`sandbox_pool/store/db.py:35-37`（所有事务都 `BEGIN IMMEDIATE`），以及 `pool_size=1`。
- 问题：只读查询（如 `head_seq`、`count_waiting`、`list_sandboxes`）也会拿写锁，和所有进程的写操作串行执行；每个排队请求每 200ms 要做一次心跳写加一次读。
- 影响：demo 规模下没有问题（测试中未观察到异常）。但副本数或排队数增加后会互相拖慢，数据库响应一慢，就会引发 M1 的心跳超时。
- 建议：只读路径用普通 BEGIN；生产环境直接换 Postgres。另外要注意：`pool_size=1` 是为了规避开发中实测到的「同进程多连接锁等待」问题（见改动说明），不能简单去掉。

**M6　E2B 连接句柄缓存只会增长，不会释放**
- 位置：`sandbox_pool/provider/e2b_provider.py:61,70`；`_forget` 只在本副本执行暂停、恢复、销毁时调用。
- 问题：由其他副本销毁、或被平台超时回收的沙箱，它们的句柄（每个都带独立的 HTTP 客户端）和锁会一直留在缓存里。
- 影响：长时间运行后内存和连接数持续增长。
- 建议：缓存加上 LRU / TTL；或者借用结束时按 `sandbox_id` 广播清理（任意副本在代为执行时发现借用已结束，就顺手清理）。

**M7　创建失败的处理分支本身可能抛异常，导致记录卡在创建态**
- 位置：`sandbox_pool/store/repository.py:359-372`（`kv_incr` 先 UPDATE、为 0 行再 INSERT），`sandbox_pool/core/maintainer.py:222-240`。
- 问题：在 Postgres 下，两个副本同时第一次创建失败时，都会 UPDATE 到 0 行然后都去 INSERT，其中一个会抛 IntegrityError（`_retry` 不会重试这种错误）；`provider.kill` 失败也会让这个分支中途退出。
- 影响：记录停在 CREATING / WARMING 状态，占着容量，直到 `op_deadline`（默认 120s）才被接管。SQLite 因为写锁串行，不会触发这个问题。
- 建议：`kv_incr` 改用 upsert（`INSERT ... ON CONFLICT DO UPDATE`），或者在初始化时预先插入这些键；失败处理分支里的每一步都单独做异常保护。

### 已核实没有问题的点

- **多副本并发抢占**：状态变更都是 CAS，容量和入队都通过池级锁行串行化。压测 20 次和两轮端到端测试中，都没有出现重复分配或超出容量。
- **对账的竞态**：列表查询前后各读一次数据库，并加 60s 宽限（配合阿里云列表接口约 1.5s 的延迟）。两轮测试中没有误删沙箱。
- **后台任务不调用 `connect()`**：已检查维护循环的全部路径，状态查询只用 `get_info` / `list`，避免了 deer-flow 那种「对账把超时一直往后推」的问题。
- **凭据**：代码、日志、git 历史中都没有 API Key 或 AccessKey（按关键字全量检索过）。
- **跨副本的连接句柄**：沙箱被其他副本暂停、恢复之后，旧的缓存句柄仍然能正常执行（场景 3 跨副本调用全部通过）。

## 4. 测试覆盖缺口

- `min_hot > 0` 且运行时间超过平台超时（H1）；多副本下的 `min_hot`（L6）。
- 续期与到期回收同时发生（M2）；`set_timeout` 出现非 NotFound 异常（M3）。
- 抢沙箱耗时超过心跳超时（M1）。
- Postgres 后端：目前完全没有测试，M7 这类问题只会在 Postgres 下出现。
- API 层：客户端断开后撤销排队、大文件上传。
- 端到端测试只检查了「10 个排队请求都拿到沙箱」，没有断言先来先服务的顺序（单元测试已覆盖）。

## 5. 建议的处理顺序

1. **上生产或对外暴露之前**：H2（鉴权、去掉 `lease_id` 暴露）；H1（如果要用 `min_hot`）。
2. **稳定性**：M1、M2、M3、M4（缩短容量占用），M7（换 Postgres 之前）。
3. **长时间运行**：M6、L7、L9。
4. **效率与脚本**：M5（换 Postgres）、L4、L5、L6、L1～L3、L8。
