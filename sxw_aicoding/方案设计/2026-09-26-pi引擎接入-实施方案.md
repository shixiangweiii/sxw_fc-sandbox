# pi 引擎接入实施方案（多引擎 agent 子系统）

> 日期：2026-09-26。调研结论见 `sxw_aicoding/技术调研/2026-09-26-pi-agent沙箱内部署与多引擎接入调研.md`。
> 目标：在现有 opencode 常驻 agent 子系统上增加 pi（pi.dev，`@earendil-works/pi-coding-agent`）引擎。接入方按 agent 自选引擎；对外接口与事件格式不变。

## 1. 决策（调研文档第 9 节，按推荐项定案）

| # | 问题 | 定案 |
| --- | --- | --- |
| 1 | 选择粒度 | **按 agent 选择**，存在 agent 设置里。切换引擎等于换沙箱，复用轮换逻辑，不做双引擎模板 |
| 2 | 谁能选 | 所有调用方都能在**已启用的引擎**中自选；管理员通过配置决定启用哪些引擎、默认引擎是哪个 |
| 3 | 桥接方式 | 沙箱内桥接进程 + **每个会话一个 `pi --mode rpc` 子进程**；桥接进程只做协议转发和进程管理 |
| 4 | 联网搜索 / MCP | 先用 `pi-mcp-adapter`（锁版本）接百炼 WebSearch MCP；PoC 不通过时改为自写的小扩展 |
| 5 | 能力差异 | 接受。pi 不支持 `agent` 参数（返回 400）；没有 webfetch（用 bash + curl）；没有权限询问 |
| 6 | 模型 | 两种引擎各自配置，默认都是 `deepseek/deepseek-flash`；暂不做按 agent 选模型 |

## 2. 本机实测补充（写方案前做的，2026-09-26，pi 0.87.1 + 真实 DeepSeek）

以下事实直接决定下文的设计：

| 事实 | 对设计的影响 |
| --- | --- |
| RPC 的 `prompt` 响应只表示已受理；事件序列以 `agent_settled` 结束；简单问答约 1.5s | 以 `agent_settled` 判完成 |
| 中止：工具结果为 `Command aborted`（`isError`）；最后一条 assistant 为 `stopReason=error`，`errorMessage="This operation was aborted"`，content 为空 | 中止状态以网关自己的中止标记为准（现有 runner 就是如此） |
| assistant 的 `usage` 含 `input / output / cacheRead / cacheWrite / reasoning / totalTokens / cost.total` | 用量可以完整映射到现有字段 |
| 会话开头有一条 `role=system` 消息 | 提取结果时跳过 |
| `--session-id <新 ID>` 可以指定新会话 ID；只设名字、没有消息的会话**不落盘**；`--session <不存在的 ID>` 进程直接退出 | 桥接进程按「会话文件是否存在」选择 `--session <路径>` 或 `--session-id <ID>` |
| `--session <ID>` 重开已有会话，消息完整 | 进程回收后可以按需重开，桥接进程重启后也能继续 |
| `-ne -e <路径>`：关闭自动发现，只加载显式指定的扩展；`-na` 忽略项目级 `.pi/` 资源 | 扩展加载由桥接进程完全控制，不受工作目录里的文件影响 |
| `session.reload()` 有进程级副作用 | 重载靠重启空闲会话进程，不调用 `reload()` |

## 3. 总体结构

```
业务系统 ──HTTP──► 网关副本（多副本，共享库）
                    └─ /v1/agents/*  AgentService
                         ├─ engines.opencode  → 沙箱（opencode 模板）: opencode serve :4096
                         └─ engines.pi        → 沙箱（pi 模板）    : pi-bridge :4096
                                                   ├─ pi --mode rpc --session … （会话 A）
                                                   └─ pi --mode rpc --session … （会话 B）
```

- 网关访问两种沙箱用**同一个 HTTP 客户端**（`agent/opencode.py`，改名为通用的 app 客户端）。桥接进程的控制接口沿用 opencode 的路径，事件和消息是 pi 的原生格式。
- 引擎差异集中在网关侧的 `agent/engines/`：事件翻译、结果提取、配置文件渲染、能力声明。

## 4. 沙箱内：pi 桥接进程（`sandbox_pool/agent/pi_bridge/pi-bridge.mjs`）

Node 单文件，零依赖。随模板安装到 `/opt/pi-agent/pi-bridge.mjs`，由守护循环 `run.sh` 拉起，监听 `0.0.0.0:4096`。

### 4.1 接口

| 接口 | 行为 |
| --- | --- |
| `GET /global/health` | `{healthy: true, engine: "pi", version, pi_version, sessions, procs}` |
| `POST /session` `{title}` | 分配 UUID，spawn 会话进程（`--session-id`），发 `set_session_name`；返回 `{id, title}` |
| `POST /session/{id}/prompt_async` `{parts: [{type: "text", text}], model?}` | 会话忙返回 409；没有进程时按会话文件重开；先生成 `run_id`，再发 RPC `prompt`；受理后返回 `{run_id}` |
| `POST /session/{id}/abort` | 会话忙时发 RPC `abort`，等它响应（最多 30s）；返回是否中止了运行 |
| `GET /session/status` | `{会话 ID: {type: "busy", run_id}}`，空闲的不列出 |
| `GET /session/{id}/run/{run_id}` | `{state: running / settled / lost / unknown}` |
| `GET /session/{id}/message` | RPC `get_messages`；进程已回收时临时重开 |
| `POST /instance/dispose` | 重启全部空闲会话进程，让新配置生效；忙的会话登记为「结束后重启」 |
| `GET /event` | SSE：第一条 `{"type":"server.connected"}`；之后每条 `{"type":"pi.event","properties":{"sessionID","runID","event"}}`；进程丢失时发 `pi.run_lost`；扩展 UI 请求发 `pi.ui_request`；每 10s 一条心跳注释 |

- 查询参数 `?directory=` 忽略。它是网关通用客户端带的，对 pi 没有意义。
- 错误统一返回 `{error}` 和对应状态码：404 会话不存在、409 忙、503 进程数达到上限、500 其他。

### 4.2 会话进程管理

启动命令：

```
pi --mode rpc --session-dir /home/user/.agent/pi-sessions
   (--session <文件> | --session-id <ID>)
   --provider <p> --model <m> [--thinking <t>]
   -ne [-e <扩展>...] -na --offline
```

- 工作目录 `/home/user/workspace`。
- `provider / model / thinking / extensions` 来自网关写入的 `/home/user/.agent/pi.json`，每次 spawn 时读取。
- stdout 按 `\n` 切分字节流，不用 `readline`；stderr 追加到 `/home/user/.agent/pi-<会话前 8 位>.log`，限制单文件大小。
- 运行状态：受理 `prompt` 时标记 busy、记录 `run_id`；收到 `agent_settled` 后 settled、空闲。
- **进程意外退出**：正在运行的 run 记为 `lost`，发 `pi.run_lost`，会话回到空闲。下次请求按会话文件重开。
- **回收**：
  - 空闲超过 `PI_BRIDGE_IDLE_S`（默认 600s）的进程关闭 stdin，有序退出；
  - 同时存活的进程数超过 `PI_BRIDGE_MAX_PROCS`（默认 8）时回收最久未用的空闲进程；都在忙时新请求返回 503。
- **扩展 UI 请求**（`extension_ui_request`）：
  - `confirm` 回答 false；`select / input / editor` 回答 `cancelled`；
  - 通知类（notify、setStatus 等）忽略；
  - 都作为 `pi.ui_request` 事件上报。无人值守下不会卡住。
- **桥接进程重启**：内存里的 run 全部丢失，查询返回 `unknown`，网关按 `lost` 处理；会话文件还在，可以继续聊。

## 5. 网关侧改动

### 5.1 引擎抽象（`sandbox_pool/agent/engines/`）

```python
class Engine:
    name: str                     # "opencode" | "pi"
    template: str; port: int; model: str
    protocol: str                 # provider.app_client 用哪种客户端（两者都是 "http"）
    supports_agent_param: bool    # opencode True；pi False
    has_runs: bool                # 是否支持 run_state（pi True）
    def translator(self, session_id: str) -> Translator      # feed(ev) -> [(kind, data)]；idle / errors / asks
    def extract_result(self, messages: list[dict]) -> tuple[str, dict, Optional[str]]
    def render_files(self, ctx: FilesContext) -> dict[str, bytes]
    def describe(self) -> dict    # 对外展示：名称、模型、能力差异
```

- `engines/opencode.py`：把 `runner.py` 里的 `Translator`、`extract_result` 和 `policy.render_opencode_config` 原样搬过来。
- `engines/pi.py`：`PiTranslator`、`extract_result_pi`，以及渲染 `pi.json`、`~/.pi/agent/mcp.json`。
- `AGENTS.md` 共用 `policy.render_agents_md`，工具提示按引擎传入。
- `engines/__init__.py`：`build_engines(cfg) -> dict[str, Engine]`。

**`PiTranslator`**（只处理本会话的 `pi.event`）：

| pi 事件 | 对外事件 |
| --- | --- |
| `message_update` / `text_delta` | `text {delta}` |
| `message_update` / `thinking_delta` | `reasoning {delta}` |
| `tool_execution_start` | `tool {tool, status: running, input}` |
| `tool_execution_end` | `tool {tool, status: completed / error, input, output / error}`（输入取自 start，内容截断） |
| `auto_retry_start` | `status {type: retry, message, attempt}` |
| `compaction_start` | `status {type: compaction, message: reason}` |
| `agent_start` | 记下 busy_seen |
| `agent_settled` | idle |
| `pi.run_lost` | errors 追加原因；idle |

- 不把 `message_end` 里的错误记到 `errors`：自动重试成功后，历史里仍有失败的那条消息。最终错误由 `extract_result` 按最后一条 assistant 判定。

**`extract_result_pi`**：
- 取最后一条 user 之后的 assistant：用量按字段求和（`cost` 取 `cost.total`），`steps` 为条数；
- 文本取最后一条有文本的 assistant；
- 最后一条 assistant 的 `stopReason` 为 `error` 或 `aborted` 时，取其 `errorMessage` 作为错误。

### 5.2 runner / service / maintainer

- **runner**：
  - `self.engine = svc.engine_for(sandbox)`，翻译和结果提取走引擎；
  - `prompt_async` 返回的 `run_id` 写入 `tasks.run_id`；
  - 跟进结束后，若引擎 `has_runs` 且有 `run_id`：查 `run_state`，结果是 `lost / unknown` 就记 `FAILED`（「agent 进程意外退出」），不把残缺结果记成成功；
  - 接管（`resume`）时从任务行读 `run_id`；
  - 自动拒绝询问只对 opencode 生效（pi 的 translator 不会产生 asks）。
- **service**：
  - `engines`、`engine_for(row)`（`row.engine` 为空视为 opencode）、`agent_engine(agent)`；
  - `client_for` 按引擎协议创建客户端；
  - `sandbox_for`：ACTIVE 沙箱的引擎与 agent 设置不一致时，CAS 为 RETIRING 后新建；`reserve_agent_sandbox` 带上 `engine` 和该引擎的模板；
  - `_boot` 用引擎的模板和端口，配置文件由引擎渲染；
  - `start_message`：引擎不支持 `agent` 参数时返回 400；
  - `update_settings`：校验 `engine` 必须在已启用的引擎里；
  - `_follow_remote` 走引擎的翻译和结果提取；
  - `agent_info` 返回 `engine`；
  - 新增 `engines_info()`。
- **maintainer**：`check_sandbox` 在「硬截止、RETIRING」判断之后、轮换判断之前，加「引擎与设置不一致」：没有运行中任务就销毁，否则转 RETIRING，记事件 `agent_engine_switch`。设置下发只在引擎一致时进行。

### 5.3 数据、配置、接口

**表结构**（只加可空列）：
- `sandboxes.engine`：NULL 视为 `opencode`，兼容已有数据；
- `tasks.run_id`：pi 的运行 ID。

**配置**（`POOL_AGENT_*`）：

| 配置 | 默认 | 说明 |
| --- | --- | --- |
| `AGENT_TEMPLATE` / `AGENT_PORT` / `AGENT_MODEL` | 现有 | opencode 引擎；配了模板即启用 |
| `AGENT_PI_TEMPLATE` | 空 | pi 模板；配了即启用 pi 引擎 |
| `AGENT_PI_PORT` | 4096 | 桥接进程端口 |
| `AGENT_PI_MODEL` | `deepseek/deepseek-flash` | pi 的模型，`provider/model` 格式 |
| `AGENT_PI_THINKING` | 空 | pi 的思考级别（空为 pi 默认） |
| `AGENT_DEFAULT_ENGINE` | `opencode` | 没有设置引擎的 agent 用哪个，必须是已启用的引擎 |

- 启动校验：至少启用一个引擎；默认引擎必须已启用；模型格式为 `provider/model`。
- 凭证注入（`AGENT_MODEL_HOST / AGENT_MODEL_API_KEY / AGENT_INJECT`）两种引擎共用，两者都用 DeepSeek，域名相同。

**接口**：
- `PATCH /v1/agents/{user_id}/settings` 新增 `engine`；
- `GET /v1/agents/{user_id}` 返回 `engine`，沙箱视图带 `engine`；
- 新增 `GET /v1/agent-engines`：已启用的引擎、默认引擎、各自的模型与能力。不放在 `/v1/agents/` 下，避免与 `{user_id}` 路由冲突；
- `POST …/messages` 的 `agent` 参数对 pi 返回 400；
- 管理员列表、统计带上 `engine`。

### 5.4 provider

- `create_app` 不变，模板由引擎决定。
- `app_client(endpoint, token, directory, *, ingress_ip)` 不变，两种引擎共用 HTTP 客户端。
- 新增一个可选参数 `run_state`，由客户端实现。
- `FakeProvider` 按模板决定沙箱里跑哪种 app（`template_apps`，默认 opencode），用于测试 pi 的内存实现。

## 6. 模板（`scripts/build_pi_template.py`）

- 基础镜像：官方 code-interpreter-v1（第二代，已配置平台 CA）。
- 启动命令（构建期执行）：
  1. 若 Node 版本低于 22.19，从 npmmirror 的 Node 二进制镜像安装 Node 24 到 `/opt/node`；
  2. `npm install --prefix /opt/pi-agent` 安装锁定版本的 `@earendil-works/pi-coding-agent@0.87.1` 和 `pi-mcp-adapter@<锁定>`，使用 npmmirror；
  3. 写入 `/opt/pi-agent/pi-bridge.mjs`（gzip + base64 嵌入）和 `run.sh`；

  5. 以 user 身份 exec 守护循环。
- `run.sh` 的环境变量：`PI_OFFLINE=1 PI_SKIP_VERSION_CHECK=1 PI_TELEMETRY=0 DEEPSEEK_API_KEY=injected-by-platform PI_BIN=… HOME=/home/user`。

## 9. 风险与预案

| 风险 | 预案 |
| --- | --- |
| 镜像 Node 过旧，或 Node 不信任平台 CA | 装 Node 24；设置 `NODE_EXTRA_CA_CERTS=/usr/local/share/ca-certificates/e2b-ca.crt` |
| `pi-mcp-adapter` 在 RPC 下卡在确认或不支持 | 自写只接百炼 WebSearch 的扩展（streamable HTTP JSON-RPC，几十行） |
| 启动命令过长（嵌入桥接脚本） | gzip 压缩；仍过长时改为构建期从 npm 镜像拉取锁定版本的桥接包，或分两段写入 |
| pi 构建期安装超过就绪等待的 5 分钟硬超时 | 就绪前只装必需的包，去掉可选依赖 |
| pi 升级带来破坏性变更 | 锁版本；桥接进程只依赖 RPC 线协议；升级 = 新模板 + 切换 |

## 10. 与方案的差异（实施中由实测驱动）

1. **桥接进程接口**：
   - 在第 4.1 节基础上，`prompt_async` 同时返回 `disposition`；
   - `run` 查询对不属于该会话的 run 也返回 `unknown`。
2. **桥接进程启动预热**：快照前没运行过 pi 时，沙箱里第一次起 pi 进程约 11s。改为桥接进程在监听端口前先起一次 pi（不建会话，`get_state` 后退出），预热结果随模板快照带进沙箱。
3. **等待 MCP 元数据缓存**：pi-mcp-adapter 的直接注册工具来自 `~/.pi/agent/mcp-cache.json`。新沙箱没有缓存时，第一条消息只能走 `mcp` 代理工具。桥接进程起会话进程时，如果启用了 MCP 且缓存不存在，先等它生成（最多 10s）。
4. **MCP 工具直接注册**：本机实测代理模式要先搜索工具名，模型常猜错、多走几步（6.6s 对 4.7s）。改为每个服务 `directTools: true`，工具名与 opencode 下一致（`websearch_bailian_web_search`）。
5. **模板启动脚本**：

## 12. 代码评审（2026-09-26）

评审报告：`sxw_aicoding/代码评审/2026-09-26-pi引擎接入代码评审报告.md`。5 个问题（高 1、中 1、低 3）已在网关侧修复，桥接进程没有改动，不需要重建模板。

- **对第 10 节第 1 条的更正**：桥接进程返回的 `disposition` 来自 pi 的 `prompt` 响应，但模板里的 **pi 0.87.1 不提供这个字段**（新版才有），桥接进程收到的都是兜底值 `started`。以 `/mcp` 等开头的消息会被 pi 当扩展命令执行、不产生运行，桥接进程因此把会话永久记为忙（PI-H1）。网关现在对以 `/` 开头的消息加空格转义，与 opencode 一样作为普通提示词。
- 建会话、发提示词的读超时从 30s 改为 150s（PI-M1），长于桥接进程的处理上限。pi 要做完 preflight（可能先压缩上下文）才响应 `prompt`。
- 下次重建 pi 模板时的后续项（桥接进程识别「命令已处理」、`prompt` RPC 单独的超时）见评审报告第五节。
