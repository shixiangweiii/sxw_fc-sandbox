## 一、结论

引擎抽象的边界划得清楚：事件翻译、结果提取、配置渲染、能力声明集中在 `engines/`，runner / service / maintainer 只多了「按沙箱记录找引擎」「引擎不一致就轮换」两类改动。opencode 的代码是原样搬迁（逐行比对过 diff），原有 147 个用例不改也能通过。多副本协调沿用 CAS 与池级锁，切换引擎复用轮换语义；run_id 用来识别进程丢失，接管、重连和健康检查都按沙箱记录找引擎。**没有发现双建沙箱、凭证进沙箱、`access_token` 泄露或破坏 opencode 行为的问题。**

本轮共 **5 个问题：高 1、中 1、低 3**，全部已修复。桥接进程（`pi-bridge.mjs`）没有改动，**不需要重建模板**。

- **PI-H1（可用性，唯一的「高」）**：用户消息以 `/mcp`、`/pi-mcp`、`/mcp-auth` 开头时（默认 MCP 配置下 pi-mcp-adapter 注册了这些命令），pi 把它当扩展命令执行，不产生运行。pi 0.87.1 的 `prompt` 响应不带 `disposition`，桥接进程无从得知，**会话被永久记为忙**：任务挂到截止时间（默认 4 小时），中止也清不掉，之后该会话的消息一律 409，runner 一直跟进到沙箱达到最长寿命。已用真实桥接进程 + pi 0.87.1 复现。同样的文本在 opencode 下是普通提示词。
- **PI-M1（正确性）**：网关客户端的读超时是 30s，而 pi 要做完 preflight（其中可能包含一次调模型的上下文压缩）才响应 `prompt`，桥接进程自身的处理上限约 141s。建会话、发提示词都是非幂等 POST，超时后不重试：网关把任务记为失败，沙箱里的运行却照常开始，会话被占住。
- **PI-L1 ~ L3**：请求拿着切换引擎前读到的 agent 快照做引擎判断（L1）；文档里的 `node --test <目录>` 在 Node 22+ 上直接失败（L2）；pi 任务的报错写成 "opencode event stream"（L3）。

## 三、逐项说明

### PI-H1（高）以 `/` 开头的消息被当作 pi 扩展命令执行

**问题**：pi 的 `prompt()` 在文本以 `/` 开头、且第一个空格前的名字是已注册的扩展命令时，直接执行命令，不产生运行（没有 `agent_start` / `agent_settled`）。沙箱里默认加载 pi-mcp-adapter（默认 MCP 配置里有百炼 WebSearch），它注册了 `/mcp`、`/pi-mcp`、`/mcp-auth`。

- 新版 pi 用 `disposition: "handled"` 告知调用方，桥接进程只认这个字段；
- **模板里的 pi 0.87.1 响应只有 `{"success": true}`**，桥接进程按「已开始运行」处理：会话标记为忙之后，再也等不到 `agent_settled`。

**影响**（真实桥接进程 + pi 0.87.1 实测）：
- 任务等不到结束事件，状态轮询一直显示忙，直到截止时间（默认 4 小时）才判为 TIMEOUT；
- 中止发给 pi 立即返回（pi 本来就空闲），但桥接进程的忙标记不变，runner 仍等不到空闲，一直跟进到沙箱达到最长寿命、被维护循环销毁；
- 期间占用一个并发任务名额（默认上限 3），该会话的消息一律 409；
- `/mcp logout`、`/mcp disable <服务>` 这类子命令还会改动沙箱里适配器的状态。

用户随手输入「/mcp 有哪些工具」就能触发。同样的文本在 opencode 下只是普通提示词，与方案「对外接口与事件格式不变」不符。

**修复**：
- `Engine.prompt_text()`（默认原样返回）。`PiEngine.prompt_text()` 在以 `/` 开头的文本前加一个空格：pi 只在文本以 `/` 开头时才尝试扩展命令、技能和提示词模板，加空格后作为普通提示词交给模型，与 opencode 一致；
- runner 发送提示词时经过 `self.engine.prompt_text()`；
- 桥接进程不改（改它要重建模板）：网关消除了唯一的触发来源（适配器的 `input` 钩子不会返回 handled）。桥接进程自身的缺陷列为后续项，见第五节。

**测试**：
- `provider/fake_pi.py` 按 pi 0.87.1 的真实行为模拟：命中 `/mcp` 等命令且 `pi.json` 开启 MCP 时不产生运行，会话一直忙；
- 新增 `test_pi_h1_slash_prompt_goes_to_the_model_not_an_extension_command`。去掉修复时，这个用例因等不到结束而超时失败。

### PI-M1（中）建会话、发提示词的超时短于桥接进程的处理上限

**问题**：`AgentHttpClient` 所有请求共用 30s 超时。非幂等 POST 读超时不重试（请求可能已生效），直接报错。而桥接进程处理这两个请求的上限：
- 等旧进程有序退出 ≤ 11s；
- 冷启动会话进程（`get_state`）≤ 60s，实测 0.5–7s；
- 等 MCP 元数据缓存 ≤ 10s；
- RPC 本身 ≤ 60s。pi 0.87.1 要做完 preflight 才响应 `prompt`，preflight 里的 `_checkCompaction(lastAssistant, false)` 在上一轮被中止或超时、且上下文超过阈值时会先压缩一次（调一次模型）。

合计约 141s。网关先超时时，任务记为 FAILED（`ReadTimeout`），而 pi 随后照常开始运行：一次无人跟进的运行，照样消耗 token；会话被占住，下一条消息得到桥接进程的 409。

**修复**：`create_session`、`prompt_async` 改用 `_SLOW_POST_TIMEOUT_S = 150s` 的读超时（连接超时不变）。这样由桥接进程先给出结果（成功或它自己的 504）。opencode 的这两个请求立即返回，不受影响；其他请求仍是 30s。

**测试**：`test_pi_m1_prompt_and_session_posts_wait_longer_than_the_bridge` 起一个每个请求延迟 0.6s 的本地服务，客户端超时设为 0.2s：
- 建会话、发提示词成功；
- 普通的 `status()` 仍按 0.2s 超时，证明延迟确实超过了普通超时；
- 去掉修复时建会话报 `ReadTimeout`。

### PI-L1（低）`sandbox_for` 按请求开始时的 agent 快照判断引擎

**问题**：`start_message` 把请求开始时读到的 agent 一路传给 `sandbox_for`。如果引擎在这期间被切换（在途请求；或准入撞上销毁后的第二次尝试），旧快照会：
- 把新引擎的 ACTIVE 沙箱当成「引擎不一致」，转为 RETIRING；
- 按旧引擎新建沙箱，随后又被维护循环按新设置轮换掉。

两个请求分别拿着新旧快照时，会来回轮换，每次都要建一个云沙箱。

**修复**：`sandbox_for` 在两处重新读库里最新的 agent，按最新的引擎设置处理：
- 发现引擎不一致、准备转 RETIRING 之前；
- 准备新建沙箱之前。

两处都不是常规路径，正常请求不多读库。

**测试**：`test_pi_l1_sandbox_for_follows_latest_engine_not_request_snapshot`。旧快照没有设置引擎、库里已设为 pi，断言 `sandbox_for` 建出 pi 沙箱；再次调用拿到同一个沙箱，没有转 RETIRING，也没有多建。去掉修复时建出的是 opencode 沙箱。

### PI-L2（低）`node --test <目录>` 在 Node 22+ 上失败

Node 22 起 `--test` 的参数按文件或 glob 解析，传目录会被当成模块入口，直接报 `Cannot find module`。CLAUDE.md、测试报告第 7 节和测试文件头注释里的命令都改为 `node --test sandbox_pool/agent/pi_bridge/test/bridge.test.mjs`。

### PI-L3（低）报错文案

runner 等待事件流连接的报错写的是 "opencode event stream …"，会进入 pi 任务的 `error` 字段，误导排障。改为 "agent event stream …"。

## 四、复核后不成立或不修的疑点

| 疑点 | 结论 |
| --- | --- |
| 桥接进程用 `-na` 启动 pi，工作目录的 `AGENTS.md`（环境说明、用户 `instructions`）会不会被忽略 | **不成立**。`-na` 只影响项目信任（`.pi/` 下需要信任的资源）；上下文文件的加载只受 `noContextFiles` 控制 |
| 桥接进程的 `ensureProc` 在新进程通过 `get_state`、MCP 缓存等待之前就把它交给并发请求 | 存在，但只影响同一会话的并发请求；网关对同一会话的任务串行，唯一的并发调用是重连时取消息快照（只读）。改动要重建模板，不修 |
| 桥接进程的 `prompt` RPC 自身 60s 超时后把 run 记为 lost，而 pi 可能随后才开始运行（压缩超过 60s） | 存在，要求 preflight 超过 60s，很少见。pi 开始运行时桥接进程会经 `agent_start` 重新记为忙，会话状态仍然一致；只是那次运行无人跟进。改动要重建模板，列为后续项 |
| 跟进结束后的 `run_state` 查询失败会让任务记为 FAILED | 这次查询紧跟在成功的取消息之后，是幂等 GET，建连 / 读失败都会重试。不修 |
| 中止请求失败后不再重试 | 两种引擎共有的既有行为（`_check_abort` 只发一次），不在本次范围 |
| pi 进程在写入本轮用户消息前崩溃，`extract_result` 取到上一轮的文本 | 这时 run 为 lost，任务状态是 FAILED，只是 `result_text` 不准。不修 |
| `validate_mcp` 不校验 `headers` / `environment` 的类型 | 既有问题，两种引擎一样透传。不修 |
| MCP 设置变更后元数据缓存过期，第一条消息先走代理工具 | 已记在测试报告 6.5「已知限制」，功能正常 |
| 桥接进程 SSE 广播不处理背压 | 网关一直在读，事件量小。不修 |

## 五、后续项（下次重建 pi 模板时一起处理）

1. **桥接进程识别「命令已处理、没有运行」**：0.87.1 的响应不带 `disposition`。可以在 `prompt` 成功后短暂等待 `agent_start`，等不到时用 `get_state` 的 `isStreaming` 确认空闲，再把 run 记为 settled；升级到带 `disposition` 的 pi 后，现有判断即可生效。网关侧的转义（PI-H1）保留，作为第一道防线。
2. **`prompt` RPC 的超时**：桥接进程对 `prompt` 用单独的、更长的超时（覆盖 preflight 压缩），并与网关的 `_SLOW_POST_TIMEOUT_S` 保持「网关更长」的关系。
3. 改桥接进程时按约定修改 `VERSION`，重建模板后 `verify`，更新 `POOL_AGENT_PI_TEMPLATE`。
