## 三、仍需修复的两个边界

### 3.1 R3-01 残留［P2］旧 runner 被接管后恢复下发，中止下一任务

**位置**：[runner.py](../../sandbox_pool/agent/runner.py) 第 235–248 行，尤其是所有权读取与 `await self.client.abort(self.session_id)` 之间。

当前检查能拦住“读取时已经失去所有权”的 runner，却不能阻止检查之后所有权发生变化。这个中止仍是按 session 生效，没有运行代次条件或会话级未决中止保护。

**本次真实验证的交错：**

1. A 的 runner 正在跟进 T1，T1 已在真实引擎中开始执行长时间 bash 工具。
2. 请求中止 T1；A 读库确认自己仍持有 T1。
3. 用内存事件门控暂停 A 的中止下发，同时暂停其心跳，模拟旧执行者停顿。没有改动数据库所有权来伪造接管。
4. 心跳实际过期后，由 B 的 `takeover_tasks` 正常 CAS 接管 T1。
5. B 的 runner 读到中止标记，向真实引擎中止 T1，T1 落库为 ABORTED。
6. 在同一个 session 启动 T2，确认 T2 的工具已开始运行。
7. 放行 A 的迟到中止。A 未重新建立有效的任务/运行约束，命令中止了 T2。

为缩短故障验证时间，专用探针设心跳 0.5 秒、接管截止 2 秒，停顿 2.5 秒；这是合法配置，走的仍是当前实现的接管路径。没有声称默认 60 秒接管配置下该问题会高频发生。

| 真实引擎 | T1 接管后的终态 | T2 终态 | T2 中止标记 | T2 错误 |
| --- | --- | --- | --- | --- |
| opencode | ABORTED | **FAILED** | **0** | `Aborted` |
| pi | ABORTED | **FAILED** | **0** | `This operation was aborted` |

T2 自己没有收到中止请求。常规 S7 和强杀后的 S10 均通过，不覆盖旧执行者之后恢复执行的情形。

**建议**：中止需要与目标运行或会话准入形成真正的协调约束，并明确接管时怎样处理前一执行者的未决中止。可以评估运行代次校验、会话级中止占用及接管时的隔离策略；当引擎只有按 session 中止的接口时，单纯再多读一次所有权仍有同类窗口。当前“确认持有后命令只会落在此任务上”的注释与实际保证不一致。

本项是原 R3-01 的故障恢复残留；原 HTTP 中止路径的修复有效，不应撤回。

### 3.2 R3-04 残留［P2］检查属于 T1，消息读取返回时已是 T2

**位置**：[service.py](../../sandbox_pool/agent/service.py) 第 828–839 行，以及第 764–766 行发送快照的位置。

`_attach_snapshot` 先读 busy 状态，pi 再核对任务的 run_id，然后取整个 session 的消息。上述读取之间允许会话进入下一轮。两轮提示词相同时，`last_prompt(messages) == task.prompt` 仍成立；消息里的最新答案已经属于 T2，却直接作为 T1 的 snapshot 发出。

订阅建立后的终态检查发生在快照发送之后，不能撤回已经发出的错误文本。

**本次真实验证没有伪造模型答案：**

1. 在同一 session 连续提交两次完全相同的提示词。
2. 提示词要求 bash 执行 Python：读取沙箱内的计数文件，加一，等待 5 秒，再输出 `R3_REAL_ROUND_<次数>`。
3. B 在 T1 忙碌、pi 的 T1 run_id 已入库时开始重连；通过了现有的 busy / run_id 检查。
4. 用事件门控延迟 B 取消息，让 T1 完成，再让 T2 在同一 session 中完成。
5. 放行 B，实际向云端引擎读取消息，收到了 T2 的答案；提示词相同，校验通过。
6. T1 的重连流先收到 T2 的快照，随后收到 T1 的正确 done。

两种真实引擎均得到：

```text
T1.result                       = R3_REAL_ROUND_1
T2.result                       = R3_REAL_ROUND_2
发给 T1 的 snapshot.delta       = R3_REAL_ROUND_2   ← 错误归属
发给 T1 的 done.result          = R3_REAL_ROUND_1
T1.state / T2.state              = SUCCEEDED / SUCCEEDED
```

**影响边界**：仍然是同一会话内的实时文本归属错误；本次最终 done 和数据库结果正确，没有发现跨用户串流。它与修复记录 6.7 中已接受的“快照与订阅之间少一段文本”不同，这里输出了另一任务的答案。

**建议**：消息读取完成后、发布快照之前，重新确认目标任务及运行边界；长期应绑定用户消息 ID / run_id 等实际身份，不能只比对提示词字符串。pi 的 run_id 检查也需要与实际取得的消息对应。应新增“相同提示词、busy/run 检查之后再跨轮读取”的回归用例。

## 六、残留问题的二次分析与修复（2026-09-28）

### 6.1 二次分析结论

两项残留都成立。修复前先在本地用内存版引擎按第三节的交错固定时序复现（两种引擎），结果与本报告的真实云沙箱结果一致：T2 被旧 runner 迟到的中止打断（opencode `The operation was aborted.`、pi `This operation was aborted`）；T1 的重连流收到 T2 的回复作为快照。

**R3-01 残留：按会话中止 + 「先确认、后下发」跨了一次网络调用。** 确认持有任务只能保证确认那一刻，命令在路上停顿期间所有权可以转移、任务可以结束、会话可以开始下一个任务；上一轮修复代码注释里「确认持有后命令只会落在这个任务上」的说法不成立。备选方案：
- 引擎按运行校验中止：opencode 1.18.32 的会话接口只有 `/:sessionID/abort` 一个中止入口（源码核实）；pi 桥接进程可以加，但要重建模板——列为后续项；
- 再多读一次所有权：检查与下发之间仍是同类窗口，不采用；
- **采用**：会话级中止占用 + 限时下发，与已有的「重载配置」同一模式（占用 90s、整体限时 60s）。

**R3-04 残留：快照的入口检查与取消息不在同一个边界内。** 复核时另发现 pi 独有的窗口：pi 回复受理（preflight 结束）之后，还要经过几次 `await emit(...)`（`agent_start`、`turn_start`、`message_start`，含扩展钩子）才把用户消息写进会话（pi-agent-core `runAgentLoop`）。这期间即使会话没换轮，`get_messages` 的最后一轮也仍是上一个任务的，提示词相同时比对文本分不出；「取消息后再读库」对它无效（任务仍是 RUNNING）。已用内存版 pi 复现：上一轮的回复 `#1` 被当成新任务的快照发出。opencode 没有这个窗口——用户消息先写入、再置忙（`createUserMessage` 在 `loop` 设 busy 之前）；但也不能靠事件认出本轮用户消息：`SessionSummary.summarize` 是 fork 出去的，算完 diff 才对用户消息 `updateMessage`，旧一轮用户消息的 `message.updated` 可能在下一轮开始之后才到。

### 6.5 对接入方的行为变化

- **中止**：语义不变（异步生效、只影响目标任务）。负责中止的副本中途停顿并被接管过、或中止下发失败时，同一会话的下一条消息会先等待占用到期（最多约 45 秒）再开始；下发失败的中止每 5 秒重试一次（原来不重试）。
- **断线重连**：不再可能收到别的轮次的快照。代价是在更多情形下不补发快照（pi：runner 记下本轮用户消息身份之前；任务刚结束时），这些情形里实时事件或随后的 `done` 仍带完整结果。

### 6.6 遗留

- 中止：进程在写出请求的同步路径上被整体冻结超过约 25s 的情形，网关无法消除；pi 桥接进程可在下次重建模板时增加「按 run_id 中止」（请求带 run_id，桥接进程只在当前 run 相同时中止），opencode 没有对应接口。
- 基础池用例 `test_l9_drain_destroys_idle_and_blocks_new_leases` 的既有偶发失败与本次改动无关，见原评审报告 6.7。
