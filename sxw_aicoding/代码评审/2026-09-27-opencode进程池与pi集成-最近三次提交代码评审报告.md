## 三、问题详情

### R3-01［P2］中止旧任务会误伤同会话的新任务

**位置**：[`sandbox_pool/agent/service.py`](../../sandbox_pool/agent/service.py) 第 788–802 行，重点是第 792 行和 796–799 行。

**原因**：`abort_task()` 先读任务，再设置 `abort_requested`，最后调用按 `session_id` 生效的远端 `abort`。这里既忽略了 CAS 的返回值，也没有把“下发中止”与该会话的新任务准入协调起来。请求中的 `task_id` 只限定了数据库更新；实际中止命令会作用于下发时该 session 正在运行的任务。

**复现 A：设置中止标记的 CAS 已失败，仍然下发 abort。**

1. 副本 A 运行任务 T1，副本 B 接收 T1 的中止请求并读到 RUNNING。
2. 暂停 B 的 `cas_task(..., abort_requested=1)`，让 T1 正常完成。
3. 在原 `session_id` 中启动 T2，确认 T2 已运行，再放行 B。
4. CAS 返回 False，但 B 继续调用 `abort(session_id)`，T2 被中止。

实际结果，两种引擎一致：

```text
abort_cas_succeeded = False
T1.state = SUCCEEDED
T2.state = FAILED
T2.abort_requested = 0
T2.error = "The operation was aborted."       # opencode
T2.error = "This operation was aborted"       # pi
```

**复现 B：CAS 成功也不能消除后续窗口。**

1. B 成功写入 T1 的 `abort_requested=1`，暂停在后续 `get_sandbox()`。
2. A 的 runner 结束本轮、看到中止标记，将 T1 记为 ABORTED。
3. 在同一 session 启动 T2，然后放行 B 的旧中止请求。
4. T2 同样被中止，且其 `abort_requested` 仍为 0；opencode、pi 均复现。

**影响**：用户中止的是 T1，实际被中止的却是后续正常提交的 T2。新任务以模型/引擎错误结束，调用方难以从自己的操作解释这个失败。

**建议**：CAS 失败时不要继续下发中止；同时应把中止命令绑定到目标运行或与会话准入串行协调，例如由仍持有该任务执行权的 runner 下发，或在支持 run_id 的协议上检查运行代次。仅加 `if not cas: return` 不足以解决复现 B。

**建议回归**：保留上述两个窗口，分别验证两种引擎；断言 T2 的运行和结果完全不受 T1 的迟到中止影响。这与已修复的 AG-M1 不同：AG-M1 修的是 T1 的终态分类，本问题是中止了错误的任务。

### R3-02［P2］引擎切换后，能力校验与实际执行引擎不一致

**位置**：[`sandbox_pool/agent/service.py`](../../sandbox_pool/agent/service.py) 第 600–603、625–629 行；同文件 `sandbox_for()` 第 321–328、342–347 行会重新读取设置并选择引擎。桥接进程 [`pi-bridge.mjs`](../../sandbox_pool/agent/pi_bridge/pi-bridge.mjs) 第 438–460 行不处理 opencode 的 `agent` 参数。

**原因**：`start_message()` 按传入的 agent 快照检查 `supports_agent_param`。随后 `sandbox_for()` 为修复 PI-L1，会在相关分支读取最新设置，并可能改为返回 pi 沙箱。任务进入实际沙箱前没有再次检查其能力，先前在 opencode 下通过校验的 `agent=plan` 便被传给 pi。

**确定复现**：

1. 请求读到尚未设置 engine 的 agent，此时默认引擎为 opencode；保留这个在途请求快照。
2. 另一个请求将该 agent 的 engine 改为 pi；尚无 ACTIVE 沙箱。
3. 用旧快照继续执行 `start_message(..., agent_name="plan")`。
4. 前置检查通过，`sandbox_for()` 按最新配置创建 pi 沙箱，任务在 pi 上成功运行。

同一探针还用最新 agent 对象发送相同请求作为对照：

```text
最新设置请求：InvalidRequest: engine pi does not support the agent parameter
在途旧快照请求：
  actual_engine = pi
  supports_agent_param = False
  agent_name = plan
  state = SUCCEEDED
  tool_events = bash running / completed       # FakePi 模拟事件
```

**影响**：接口本应对 pi 的 `agent` 参数返回 400，却静默接受。`plan` 所代表的 opencode 规划模式不会在 pi 中生效；同样的问题也适用于其他依赖 opencode agent 配置的调用。本次确认的是参数被错误接受及转交的代码路径，未执行真实模型或文件修改来验证其后果。

**建议**：完成实际沙箱选择后，按 `engine_for(row)` 校验引擎专属参数，在插入任务前拒绝不支持的组合；包括换沙箱重试路径。已有 PI-L1 的设置刷新应保留。

**建议回归**：请求读到 opencode 设置、随后切换 pi、再继续带 `agent=plan` 的请求，必须得到与最新设置请求一致的拒绝结果，且不能向 pi 发送 prompt。现有 PI-L1 用例只断言创建了最新引擎的沙箱，没有覆盖前置能力校验与实际引擎的组合。

### R3-03［P2］并发修改不同设置字段时，后写请求会丢掉前写请求的变更

**位置**：[`sandbox_pool/agent/service.py`](../../sandbox_pool/agent/service.py) 第 289–296 行；[`sandbox_pool/store/agent_repo.py`](../../sandbox_pool/store/agent_repo.py) 第 91–106 行。API 在 [`agent_routes.py`](../../sandbox_pool/api/agent_routes.py) 第 107–112 行读取 agent 后调用此路径。

**原因**：`update_settings()` 用请求开始时的 `agent.settings` 快照合并 PATCH，然后把整个 JSON 交给 `update_agent()` 覆盖。存储层虽然增加 `settings_version`，但 UPDATE 的条件只有 agent ID，没有期望版本，也没有在同一事务中重新读取当前设置再合并。

**确定复现**：

1. 两个请求均读取初始 `settings={}`。
2. 请求 A PATCH `{"engine":"pi"}`，写入成功。
3. 请求 B 用自己先前读取的快照 PATCH `{"instructions":"KEEP THIS INSTRUCTION"}`。
4. B 未修改 engine，却把它从存储中移除了。

实际结果：

```json
{
  "stored_settings": {"instructions": "KEEP THIS INSTRUCTION"},
  "effective_engine": "opencode"
}
```

**影响**：两个请求修改的是不同字段，也会互相覆盖。对最新引入的 engine 字段而言，普通说明更新可能撤销刚成功的引擎选择；维护循环随后按被覆盖的设置继续工作。相同整包更新机制也影响 MCP 与空闲销毁等设置。

**建议**：把“读取最新设置、应用本次 patch、递增版本”放到同一受协调的存储事务中，或按期望版本 CAS 并在冲突后重新合并。只在 service 中多读一次、随后继续无条件 UPDATE，仍会留下同类窗口。

**建议回归**：两个副本同时修改不同字段，最终两项都保留；另测同字段冲突的既定语义和 `engine=null` 恢复默认。已有 AG-L7 是平台出网策略与数据库版本的下发竞态，并不是这项数据库内的设置丢失问题。

### R3-04［P2］跨副本重连流会混入其他轮次的文本

**位置**：[`sandbox_pool/agent/service.py`](../../sandbox_pool/agent/service.py) 第 745–755、767–779 行；[`engines/pi.py`](../../sandbox_pool/agent/engines/pi.py) 第 48–53 行的事件过滤只检查 session，没有检查 runID。

**原因**：`_follow_remote()` 要跟进的是某个 task，但快照与事件订阅都只按 `session_id` 取数据；快照取会话“最后一轮”的结果，事件持续转发到下一次数据库终态轮询。会话可以在 T1 结束后继续 T2，因此 session 不能唯一标识一次任务。

**复现 A：T1 的重连流包含 T2 的输出。**

1. 副本 A 执行 T1，副本 B 订阅 T1 的任务流。
2. 等 T1 完成，立即在同一 session 中提交 T2。
3. B 尚未到下一次约 1 秒的任务状态轮询，继续转发该 session 的新事件。

opencode 和 pi 均得到：

```text
T1 流中拼接的 text：echo: [sleep:0.3] FIRST_ROUNDecho: SECOND_ROUND
T1 的 done.result：echo: [sleep:0.3] FIRST_ROUND
contains_second_round = True
```

**复现 B：新任务的快照包含上一轮答案。**

1. T2 已完成，在同一 session 中启动 T3。
2. 暂停 T3 的 `prompt_async`，模拟提示词尚未送达/写入会话的窗口。
3. 另一个副本重连 T3，快照读取的仍是 T2 的最后一轮消息。

两种引擎都给 T3 发出：

```text
text = {"delta": "echo: SECOND_ROUND", "snapshot": true}
```

**影响与边界**：实时文本会显示错误轮次的内容。当前实测最终 `done.result` 和数据库中的 T1 结果仍正确，未发现跨用户数据串流；因此本项不定为最终结果存储损坏或跨用户泄漏。手册要求最终回复为准可以减轻影响，但不能让错误的任务增量成为正确行为。

**建议**：事件和快照都应绑定到目标任务的运行/消息边界；pi 可利用已有 runID，opencode 需要明确本轮消息边界。目标任务结束后停止转发后续轮次；未确认本轮消息已经存在时，不把上一轮结果当作本轮快照。仅缩短数据库轮询间隔不能消除问题。

**建议回归**：同一 session 连续两轮、跨副本跟流，T1 的流不得出现 T2 标记；在新 prompt 尚未进入引擎时重连，不得返回上一轮文本。已有重连用例主要覆盖单轮任务最终完成，没有同时验证相邻轮次隔离。

### 6.2 修复方案与取舍

- **R3-01：中止命令只由持有任务的 runner 下发。**
  - `abort_task` 只写 `abort_requested`，不再直接按会话中止；CAS 失败说明任务已经结束，返回 409。本副本有 runner 时通知它。
  - runner 每秒读一次库（`_DB_POLL_S`；原来随 5 秒一次的状态轮询），查到其他副本写的中止标记。下发中止前（包括本地请求和超时）读库确认仍持有任务（RUNNING 且 `op_owner` 是自己），否则按失去所有权退出。任务在库里 RUNNING 期间同一会话不会准入新任务（`create_task` 的 `session_busy`），命令只会落在这个任务上。
  - 负责副本崩溃、还没人接管时收到的中止只记标记，接管的副本开始跟进后立即下发。
  - 没有采用的方案：按 run 中止要改桥接进程（重建模板），opencode 也没有这样的接口；在库里加「会话级中止栅栏」让准入等待，需要新列，并与准入、超时联动，复杂度高于收益。
- **R3-02：以实际沙箱的引擎为准。** `_start_task` 在插入任务前按 `engine_for(row)` 校验 `agent` 参数，覆盖续聊、新会话和换沙箱重试。`start_message` 按请求快照的前置检查保留，只用来避免为注定被拒绝的请求建沙箱。代价：在途请求可能已经按新设置建好了 pi 沙箱才被拒绝，这是 agent 当前的引擎，后续请求会复用。
- **R3-03：读、合并、写放进同一事务。** 新增 `AgentStore.patch_settings`：池级锁内读最新设置，合并 patch（值为 None 的键表示恢复默认，从设置里删除），写回并把版本号加一。`update_agent` 只保留出网策略的整体替换（PUT 语义）。
- **R3-04：按轮次划清重连流的归属**（`_follow_remote`、`_attach_snapshot`，两种引擎共用）：
  - 快照只在确认会话正在运行这个任务那一轮时补发：会话在 `/session/status` 里忙；pi 还要求忙碌项的 `run_id` 等于任务的 `run_id`；最后一条用户消息等于 `engine.prompt_text(任务提示词)`。否则不补发——这一轮还没开始时，它的事件随后会到；刚结束时，`done` 随后带来最终结果；
  - 翻译器新增 `round_starts`（opencode：新的用户消息；pi：`agent_start`；可以多报，不能漏报）。订阅建立时、会话开始新一轮时立即读库，任务已结束就发 `done` 退出，不转发之后的事件；
  - 这一轮结束（idle / agent_settled）之后的事件不再转发。
- **R3-N1：正在输出的消息以全文为准。**
  - opencode 翻译器：缓存的增量不是部件全文的开头时，判定为中途接入的片段，丢弃缓存，按部件结束时的全文输出。正常路径（先收到空文本的开始事件，或缓存正是开头）不变；
  - pi 翻译器新增 `mid_round`，由跟随者和接管的 runner 设置：没看到 `message_start` 的 assistant 消息不转发增量，`message_end` 时按全文输出（思考、正文）。runner 从头跟进时不受影响；
  - 内存版 pi 补上真实 pi 的 `message_start`。

### 6.6 对接入方的行为变化

- **中止**：异步生效。返回时任务通常仍是 RUNNING，约 1 秒内结束为 ABORTED（原来由接收请求的副本立即下发）；负责副本崩溃时，等心跳过期（默认 60 秒）、其他副本接管后才生效。读到 RUNNING 之后任务恰好结束的，返回 409（原来返回 200，同一会话若已开始下一个任务，还会把它中止）。
- **断线重连**：只含本任务那一轮的输出；本轮还没开始或刚结束时不补发快照；重连时正在输出的那条消息，等它输出完整条补发。
- **修改设置**：并发修改不同字段都保留，同一字段以后提交的为准。
- **`agent` 参数**：以实际执行任务的引擎为准，切换引擎期间的在途请求同样返回 400。

### 6.7 遗留与后续

- **重连流的边缘缺口**：取快照与建立订阅之间刚好输出完的消息，既不在快照里，也收不到它的事件，重连流会缺这一段（毫秒级窗口，`done.result` 完整）。彻底消除需要引擎提供带序号、可回放的事件流，暂不处理。
- **快照只含本轮最后一条有文本的消息**：多步回复（先说明、再调工具、再回答）中途重连时，前几步的文本不补发。这是既有语义（与 `extract_result` 一致），未改。
- **跨副本中止的延迟**取决于 runner 每秒一次的读库；负责副本崩溃时要等心跳过期后由接管方下发。
- 历史遗留项（AG-L6、AG-L7、AG-L9 等）与 pi 评审第五节的桥接进程后续项不变。
- **基础池用例的既有偶发失败（与本次改动无关，未改）**：全量连跑中 `tests/test_review_fixes.py::test_l9_drain_destroys_idle_and_blocks_new_leases` 失败过 1 次（`destroyed` 为 3，期望 4）。原因：`pool.drain()` 写入排空标志后自己调用 `drain_idle()`，基础池维护循环（测试配置每 0.05s 一轮）看到标志后也会调用 `drain_idle()`，两边抢同一批行的 CAS，`drain()` 只统计自己赢下的数量。在排空标志写入后稍作停顿，即可在修改前的 HEAD 上确定复现：`drain()` 返回 0，但 4 个空闲沙箱都已销毁、只剩借出中的。受影响的只是返回值和这条断言。建议断言终态（没有空闲 / 暂停的沙箱、只剩借出中的），或让 `drain()` 按排空前后的空闲 / 暂停沙箱数计算。基础池不在本轮评审范围。

### 6.8 验收后续（2026-09-28）

验收报告 `2026-09-27-9f265ba修复二次复核与真实云沙箱验证报告.md` 在真实云沙箱上复现了本轮修复的两处残留，均已修复，记录见该报告第六节：

- **R3-01**：6.2 中「下发前确认仍持有任务，命令只会落在这个任务上」不成立——确认之后旧 runner 可能停顿、心跳过期被接管，任务结束、同一会话开始下一个任务，迟到的命令仍会中止它。现改为下发前在库里占住会话、限时下发（短于占用），占用期间同一会话不准入新任务。
- **R3-04**：6.2 的快照条件只在取消息之前检查，取消息期间会话可能换轮；pi 还存在「受理之后、用户消息写入之前」的窗口。现改为取消息之后再读库确认，pi 另按用户消息身份（带 runID 的事件里的时间戳）绑定。
