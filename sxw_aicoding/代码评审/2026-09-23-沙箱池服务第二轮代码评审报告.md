## 四、高优先级问题详解

### R2-H1 客户端在「抢到沙箱之后、响应发出之前」断开，沙箱泄漏整个借用期

**位置**：`sandbox_pool/core/allocator.py:144-148`

```python
except asyncio.CancelledError:
    await asyncio.shield(self.store.cas_waiter(seq, WaiterState.WAITING, WaiterState.CANCELLED))
    raise
```

**问题**：`claim_ready`（`repository.py:263-287`）与 `finish_resume`（`repository.py:288-314`）提交事务的那一刻，三件事已经同时落库：借用记录 ACTIVE、沙箱 LEASED、排队记录 GRANTED。而这个 `except` 分支只撤销排队记录，**不结束已授予的借用**。

取消可能落在提交之后的位置至少有 3 处 await：

1. `allocator.py:141` `return await self._hand_over(grant, ...)`（内部还有 `is_disconnected()` 与可能的 `end_lease`）；
2. `routes.py:56` `await pool.allocator.get_lease(grant.lease_id)`（构造响应体时又读一次库）；
3. 响应写回客户端失败。

**触发条件**：uvicorn 优雅停机 / 重启取消在途任务、客户端在拿到响应前断开且服务端取消了处理协程。注意 `_hand_over` 里的 `is_disconnected()` 检查**覆盖不了这条路径**——它只处理「Starlette 报告断开但任务未被取消」的情形，且必须先跑到 `_hand_over` 才有机会执行。

**后果**：

- 沙箱被占住 `lease_ttl_s`（默认 600s），期间池容量 -1；
- `fix_orphan_leased`（`maintainer.py:162-168`）不会回收，因为借用是 ACTIVE；
- `expire_leases` 要等到 `expires_at` 才回收；
- **没有人工恢复手段**：`GET /v1/sandboxes` 故意隐藏 `lease_id`（这个决定本身是对的，见 `routes.py:116-121`），运维无法把卡住的沙箱映射到借用并强制释放，只能直连数据库改记录（见 R2-L6）。

**建议方向**：把 `grant` 变量提到 `try` 之外，在 `except CancelledError` 分支（或统一在 `finally`）里判断「已获得 grant 但尚未返回给调用方」，若是则 `end_lease(grant.lease_id, RELEASED, "request cancelled")`；同时补 R2-L6 的管理接口作为兜底。

### R2-H2 保活失败的回滚是版本条件 CAS，失败后留下「谎报的 `platform_deadline`」并永久抑制重试

**位置**：`sandbox_pool/core/maintainer.py:243-267`

```python
if not await self.store.cas_sandbox(
    row["id"], [SandboxState.READY], now=now,
    expect_version=row["version"], platform_deadline=now + timeout,   # ① 乐观预写
):
    return
try:
    await self.provider.set_timeout(row["provider_id"], timeout)
except Exception as e:
    await self.store.cas_sandbox(
        row["id"], [SandboxState.READY], now=self.lc.now(),
        expect_version=row["version"] + 1,                            # ② 回滚也带版本条件
        platform_deadline=row["platform_deadline"],
    )
    return
```

**问题**：②的回滚带 `expect_version = v+1`，**只要期间发生过任何一次版本变更就会静默 no-op**（返回值未被检查，也未记日志）。而 `keepalive_ready`（`maintainer.py:234-241`）的判据是 `deadline - now >= timeout/2 → continue`，因此一个偏大的 `platform_deadline` 会让这个沙箱**在之后数小时内再也不被保活**。

**可达的两副本交错**（我推演了全部分支，只有这一条是坏的）：

| 步骤 | 副本 A | 副本 B | 库中 `platform_deadline` | 云端实际 TTL |
|---|---|---|---|---|
| 1 | 读到 v，deadline=D（短） | 读到 v，deadline=D | D | 短 |
| 2 | CAS v→v+1 成功，写 D_A（远） | CAS（expect v）失败 → 跳过 | D_A | 短 |
| 3 | `set_timeout` **失败** | 下一轮读到 v+1，CAS v+1→v+2 成功，写 D_B | D_B | 短 |
| 4 | 回滚（expect v+1）**no-op** | `set_timeout` **也失败** → 回滚到它读到的值 **D_A** | **D_A（谎报）** | **短** |

结果：云端按旧的短 TTL 回收这个 READY 沙箱，而库里认为它还有数小时寿命，保活直接跳过。

**其余版本变更分支都是良性的**（我逐个核对过）：转 PAUSING / LEASED / DESTROYING 时，胜出方都会自己写或清空 `platform_deadline`；另一副本保活成功时云端确实被续期，值也是对的。

**后果**：

- `min_hot` 保留的热沙箱凭空消失——正是上一轮 H1 想修的场景，只是换了一条路径；
- 或借用方 `_claim_ready` 拿到 `SandboxNotFound` → 借用 FAILED → 调用方 502；
- 只能靠 60s 一次的对账（`maintainer.py:401-441`）发现「云端已消失」并清理记录，期间容量与延迟都受影响。

**建议方向**：失败时**无条件**把 `platform_deadline` 置为 `None`（只带 state 条件，不带版本条件）。`None` 会让下一轮 `keepalive_ready` 立刻重试，语义上比「恢复到旧值」更安全，也消除了对版本竞态的依赖。更彻底的做法是取消乐观预写、成功后再写，但那样会丢掉 CAS 占位的互斥性，需要权衡（可考虑用 `op_owner` 占位）。

## 五、中优先级问题详解

### R2-M1 `warmup()` 硬编码 `_handle(sandbox_id, 300)`，缓存未命中时会把云端超时改成 300s

**位置**：`sandbox_pool/provider/e2b_provider.py:175-179`

```python
async def warmup(self, sandbox_id: str, code: str) -> None:
    h = await self._handle(sandbox_id, 300)      # ← 300 是硬编码
```

`_handle`（`e2b_provider.py:146-163`）在缓存未命中时走 `AsyncSandbox.connect(timeout=int(timeout_s), ...)`，而 **connect 会重设平台超时**。`_create_one` 传的是 `ready_platform_timeout_s`（`config.py:75-77`）：

- `pause_enabled=true` → 180s，比 300s 短，**方向安全**（库里 `platform_deadline` 更早，保活会提前续期）；
- `pause_enabled=false` → `ready_platform_timeout_s = max_age_s = 21600`。此时 `maintainer.py:350` 写入 `platform_deadline = created_at + 21600`，保活判据 `>= 10800s` 直接跳过，但**云端会在 300s 回收**——每个 READY 沙箱 5 分钟静默死亡，对账才发现，池子持续抖动。

**当前不爆发的原因**：`create()`（`e2b_provider.py:172`）会把句柄放进缓存，同副本紧接着 warmup 命中缓存、不触发 connect。但这是一层薄冰：句柄被 LRU 或空闲淘汰（`handle_cache_max=64`，容量调大就可能）、或预热逻辑在别处重放，问题立刻生效。

**建议**：把这里的 `300` 换成调用方传入的 `ready_platform_timeout_s`（`warmup` 签名加一个 `sandbox_timeout_s` 参数，与 `run_code` 等保持一致）。

### R2-M2 provider 请求超时是模块常量、不从配置派生；文档教的 e2e 配置本身就打破了不变量

**位置**：`sandbox_pool/provider/e2b_provider.py:36-40`（常量）、`169`（create）、`188`（pause）

项目自己写下的不变量（CLAUDE.md 与 `e2b_provider.py` 文件头注释）：**「各调用的请求超时必须小于对应的截止时间」**。核对结果：

| 调用 | 传入的 `request_timeout` | 实际生效值 | 对应截止时间 | 默认配置 | `POOL_OP_TIMEOUT_S=60` |
|---|---|---|---|---|---|
| `kill` | `_KILL_TIMEOUT` | 20s | `destroy_timeout_s`=30 | ✅ | ✅ |
| `connect`（恢复） | `_CONNECT_TIMEOUT` | 30s | `resume_timeout_s`=60 | ✅（30+15<60） | ✅ |
| `set_timeout` / `get_info` / `list` | `_API_TIMEOUT` | 30s | — | ✅ | ✅ |
| **`create`** | **未传** | **SDK 默认 60s** | `op_timeout_s`=120 | ✅ | ❌ **60 ≮ 60** |
| **`pause`** | **未传** | **SDK 默认 60s** | `op_timeout_s`=120 | ✅ | ❌ **60 ≮ 60** |
| **`create` + `warmup`** | warmup 传 `timeout=60`（命令超时） | 60 + 60 = 120s | `op_timeout_s`=120 | ⚠️ 刚好等于 | ❌ **120 > 60** |

我确认了 `AsyncSandbox.pause` 与 `create` 的签名都接受 `**opts: Unpack[ApiParams]`（`e2b/sandbox_async/main.py:625-657`、`178`），其中就包含 `request_timeout`——**能传，只是没传**，于是回落到 `e2b/connection_config.py:12` 的 `REQUEST_TIMEOUT = 60.0`。

**为什么这条要紧**：CLAUDE.md 的「常用命令」和 README 的端到端章节都明确写着 `export POOL_OP_TIMEOUT_S=60`。也就是说，**照着文档做端到端测试时，这个不变量就是被打破的**。后果是健康但偏慢的创建/暂停被其他副本判为卡死并接管销毁（`maintainer.py:117-131`），表现为「创建/暂停偶发失败、沙箱被销毁重建、账单白花」。实测暂停 p50 14.6s / p99 15.8s，离 60s 还有距离，所以端到端侥幸通过了——这是配置耦合的定时炸弹，不是已暴露的故障。

**建议**：把这些常量改为从 `PoolConfig` 派生（例如 `min(模块常量, deadline × 0.5)`，由 `E2BProvider` 构造时接收配置），或在 `PoolConfig.from_env` 里校验并拒绝 `op_timeout_s` 小于「create + warmup 预算」。

### R2-M3 排空不会快速失败「排在别人后面」的等待者

**位置**：`sandbox_pool/core/allocator.py:135-141`

```python
if ahead < available or ahead == 0:
    if await self._draining():                      # ← 排空检查只在分支内
        await self.store.cas_waiter(seq, WAITING, CANCELLED)
        raise PoolDraining("pool is draining")
    grant = await self._try_claim(...) if ahead < available else None
    ...
await asyncio.sleep(self.cfg.poll_interval_s)
```

当 `ahead >= 1 且 available == 0`（前面有人、当下没有可分配沙箱）时，循环只是 sleep 后重算，**永远看不到 draining**，只能等到 `wait_timeout_s`（默认 180s）耗尽返回 **504**。

`test_l9_drain_fails_queued_waiters_fast` 用的是 `max_size=1` 且只有 1 个等待者（`ahead == 0`），恰好走的是被覆盖的分支，所以测试是绿的但语义没覆盖全。

**影响**：调用方拿到 504（等待超时）而不是 503（池子排空中），会按「偶发超时」重试而不是按「池子在维护」退避，排空期间反而制造更多请求。

**建议**：把 `_draining()` 检查提到分支之外，每轮循环都做（成本是一次 `kv_get` 只读查询）。

### R2-M4 请求恰好在暂停进行中到达时，要白等一次完整的暂停 + 恢复（实测约 17s）

**位置**：`sandbox_pool/core/maintainer.py:187-188`、`sandbox_pool/core/allocator.py:163-170`

`pause_idle` 只在 tick 开头检查一次 `count_waiting() > 0`；检查通过后发起的 PAUSING **不会因随后到达的请求而中止**。同时：

- `_try_claim` 只列 READY 与 PAUSED，**PAUSING 对借用方完全不可见**（`allocator.py:167-170`）；
- `queue_position` 的 `available` 也不含 PAUSING（`repository.py:35`）。

于是请求只能干等暂停跑完，再走恢复：实测暂停 p50 14.6s / p99 15.8s（多个同时暂停更慢），恢复 2.3~2.8s，**合计约 17s**。

**为什么这条值得单列**：默认 `idle_pause_after_s=60`，「池子空闲一分钟后来了第一个请求」正好撞进这个窗口，是最常见的真实路径之一，而不是边缘情况。

**建议**：暂停过程中若出现等待者，让 PAUSING 的行可被抢占（例如 `_claim_paused` 也接受 PAUSING，等 pause 完成后立刻 resume），或给 `_pause_one` 加一个「发现等待者就放弃本次暂停」的检查点；至少应在 `/v1/pool/stats` 里把这个延迟暴露出来，便于定位。

### R2-M5 除 `PUT files` 外没有任何请求体大小限制

**位置**：`sandbox_pool/api/app.py:65-69`（无中间件）、`routes.py:25-36`（`_read_body` 只被 `write_file` 使用）

`POST /v1/leases/{id}/run_code` 的 `code` 字段是普通 JSON body，Starlette 默认不限长。一个持有合法 key 的调用方（或泄漏的 key）可以 POST 一个数 GB 的 body 把副本 OOM 掉。而副本共享同一个 SQLite 写连接，**一个副本卡住会拖慢全池**（`store/db.py:32-35` 的 `pool_size=1`）。

已安装的 starlette 里就有现成的 `middleware/body_limit.py`（我确认过文件存在）。

**建议**：全局加 body limit（与 `max_upload_bytes` 同量级或更小），`PUT files` 保留自己的流式计数以便精确返回 413。

### R2-M6 没有按调用方的配额，单个客户端可以吃满全池

**位置**：`sandbox_pool/core/allocator.py`、`api/auth.py`

`max_size` / `queue_max` 都是**全池**维度，`client_id` 只用于归属校验（`allocator.py:269-275`）。一个调用方可以：

- 占满全部 5 个借用，且 `acquire` 的 clamp（`allocator.py:96`）允许直接请求 `lease_ttl_s = lease_max_s = 3600s`；
- 再占满 10 个排队位。

其他调用方全部 429/504。多租户场景下这是典型的「一个坏邻居饿死所有人」。

**建议**：增加 `per_client_max_leases` / `per_client_max_waiting`，在 `reserve_slot` / `enqueue` 的**同一事务内**按 `client_id` 计数——正好可以复用现有的 `pool_kv.lock` 串行化机制，不需要新的协调原语。

### R2-M7 `_use` 在每次代为执行时都写一次库，而这个写入没有任何读者

**位置**：`sandbox_pool/core/allocator.py:316` → `store/repository.py:244-248`

```python
await self.store.touch_sandbox(lease["sandbox_row_id"], now)   # 每次 run_code / commands / files 都执行
```

我 grep 了 `last_active_at` 的**全部读点**：`maintainer.py:190`（列 READY 排序）、`maintainer.py:195`（判空闲）、`allocator.py:167`（列 READY 排序）——**三处都只查 READY**。而借用结束后沙箱必定销毁（设计如此：「归还即销毁」），永远不会回到 READY，所以 **LEASED 行的 `last_active_at` 从来没被读过**。

代价：每次 `run_code` / `commands` / `files` 都白付一次写事务。在 SQLite 上要抢那个**每进程唯一的写连接**（`db.py:32-35`）和文件写锁，与补货、暂停、心跳、过期回收排队；换 Postgres 后也是一次无意义的行更新与 WAL 写入。这是热路径上最容易摘掉的成本。

**建议**：直接删掉 `allocator.py:316` 这一行（`touch_sandbox` 若无其他调用方，一并移除）。

### R2-M8 `HandleCache.pop` 会删掉锁对象，导致两个并发 `_handle` 各拿一把锁、双双 connect

**位置**：`sandbox_pool/provider/e2b_provider.py:100-107`

```python
def pop(self, key: str) -> None:
    self._items.pop(key, None)
    lock = self._locks.get(key)
    if lock is not None and not lock.locked():
        del self._locks[key]

def lock(self, key: str) -> asyncio.Lock:
    return self._locks.setdefault(key, asyncio.Lock())
```

`lock()` 返回的锁对象，可能在调用方真正 `async with` 之前就被另一次 `pop` / `_evict`（`e2b_provider.py:113-122`）从字典里删掉；第三个调用方 `setdefault` 会得到**一把新锁**，于是两边同时进入临界区 → 对同一个沙箱并发 `connect()`。

`forget()`（暂停、恢复、销毁、借用结束都会调用）和 `_evict()` 都会触发这条路径，并发借用下并非纯理论。

**后果**：多一次 connect（会重设平台超时，机制见 R2-M1）；后写入的句柄覆盖前一个，被覆盖的句柄失去引用（其 httpx client 共享 SDK 的 transport，不至于关掉连接池，但白占资源，且 `_handle` 的互斥意图落空）。

**建议**：锁字典只增不删（按 `handle_cache_max` 同量级封顶即可），或改用引用计数 / `weakref` 清理。

### R2-M9 `kv_set` / `kv_incr` 仍在用「UPDATE 失败再 INSERT + integrity_retry」——正是 §4.1 那个死锁的模式

**位置**：`sandbox_pool/store/repository.py:502-527`

`docs/sandbox-pool-fix-changes.md` 4.1 已经把根因写得很清楚：**执行失败的语句在 SQLAlchemy 的 aiosqlite 适配层不会关闭游标，之后被主线程的循环 GC 回收时要拿该连接的 SQLite 互斥锁，而该连接的工作线程可能正在 `BEGIN IMMEDIATE` 的忙等中持有它 → 事件循环被卡住，同进程内持有写锁的协程无法提交，死锁到 busy_timeout（30s）**。

`init_schema` 已经改成「先查已有键、只插缺失的」（`repository.py:128-136`，注释也写明了原因）。但 `kv_set` 与 `kv_incr` 还保留着 UPDATE-then-INSERT + `integrity_retry=True` 的写法。

**今天不爆发的唯一原因**：`_KV_KEYS`（`repository.py:31`）里的 6 个键在启动时都预置了，UPDATE 必然命中，永远走不到 INSERT。**任何人新增一个 kv 键而忘了登记进 `_KV_KEYS`，就会把这个死锁重新引进来**，症状还是那个极难复现的 30s 卡顿。

**建议**：改成方言无关的 upsert（`sqlalchemy.dialects.sqlite.insert(...).on_conflict_do_update(...)`，Postgres 同语法），彻底不依赖「预期失败的语句」；或退一步，加一条测试断言「源码中出现的所有 kv 键都在 `_KV_KEYS` 中」。

### R2-M10 文件上传/下载继承 30s 请求超时，与 64 MiB 的上限自相矛盾

**位置**：`sandbox_pool/provider/e2b_provider.py:156`（`request_timeout=_CONNECT_TIMEOUT`=30）→ `filesystem.py:207,360`

`_handle` 用 `request_timeout=30` 建立连接，这个值会存进句柄的 `ConnectionConfig.request_timeout`（`connection_config.py:156-159`）。而 SDK 的 `files.write` 用的是：

```python
upload_timeout = self._connection_config.get_request_timeout(request_timeout)   # filesystem.py:360
```

池子调 `h.files.write(path, data)`（`e2b_provider.py:279`）**不传 `request_timeout`** → 回落到 30s。`files.read` 同理。

配置上 `max_upload_bytes = 64 MiB`（`config.py:68`），但 64 MiB 在 30s 内传不完就直接 502——经 HTTP 代理出网时更容易触发。

**建议**：在 `write_file` / `read_file` 里显式传 `request_timeout`，按 `max_upload_bytes` 与预期带宽估算一个上限。

### R2-M11 用户代码超时被映射成 502，与「沙箱后端故障」不可区分

**位置**：`provider/e2b_provider.py:252` → `core/allocator.py:_guard`（`allocator.py:319-328`）→ `api/app.py:25-35`

SDK 在代码执行超时时抛 `format_execution_timeout_error()`（`code_interpreter_async.py:234-235`，由 `httpx.ReadTimeout` 触发）。`_guard` 的兜底 `except Exception` 把它包成 `SandboxOpError` → **502**。

但 README / 设计文档写的是「`run_code` 返回 stdout、stderr、text、results（含图片）、**error**」，调用方合理预期「我的代码超时了」是一个 `error` 结果或 4xx，而不是与「云沙箱挂了」同一个 502。**502 通常会触发客户端重试，而重试会把非幂等的代码再跑一遍**（可能重复写文件、重复发请求、重复扣费）。

**建议**：在 `_guard` 里识别超时类异常，返回 `error={"name": "TimeoutError", ...}` 或映射为 408/504，并在接口文档里写明。

### R2-M12 `release()` 在销毁失败时仍返回 200，但容量还被占着

**位置**：`sandbox_pool/core/lifecycle.py:74-88`、`core/allocator.py:300-308`

`finish_destroy` 里 `provider.kill` 抛异常时只记日志就 `return`，**不删除行**（这是对的，留给 `op_deadline` 重试）。但 `end_lease` 仍返回 True，`release` 返回 `200 + state=RELEASED`。

调用方以为已经归还，实际上：沙箱行停在 DESTROYING，**继续占用容量最多 `destroy_timeout_s`（30s）**，期间新借用会排队甚至 504。另外 `end_lease` 返回 False（借用早已结束）时 `release` 也是静默 200。

**建议**：响应体里带上「销毁是否已完成」（例如 `destroyed: bool`），或至少把未完成的情况记成事件让 `/v1/pool/stats` 可见。

## 六、低优先级问题

### R2-L1 PAUSED 行不跟踪 `platform_deadline`

`start_pause`（`repository.py:338`）把 `platform_deadline` 置为 None，之后没有任何逻辑跟踪暂停中沙箱的平台到期时间。若「TTL 在暂停期间仍累计、resume 不重置」成立（`docs/fc-agent-sandbox-notes.md` 第 4 节标注为 **[待核实]**），暂停的沙箱会在若干分钟后被平台静默回收，只能靠对账发现。

**建议**：实测确认这条平台行为；若成立，PAUSED 也要记录到期时间并纳入 `retire_old` 的回收决策，避免借用方 resume 一个已被回收的沙箱。

### R2-L2 `PoolConfig.from_env` 零校验

`config.py:84-99` 只做类型转换，不校验取值：

- `queue_max < 0` → `enqueue` 的 `n >= queue_max + avail` 恒真 → 全部 429；
- `idle_pause_after_s = 0` → 沙箱建好就暂停；
- `target_size > max_size` → 只在 `replenish`（`maintainer.py:296`）用 `min()` 兜了一处，其他读取点没有；
- `max_size = 0` → 池子永不补货，所有借用 504；
- `POOL_API_KEYS` 格式错 → 在 `create_app` 里抛裸 `ValueError` traceback，而不是一条清晰的启动错误。

**建议**：加一个 `validate()`，在 `from_env` 之后、启动之前调用，非法配置直接拒绝启动并给出明确信息。

### R2-L3 `examples/__pycache__/*.pyc` 被 git 跟踪

`git ls-files` 显示 `examples/__pycache__/create_gen2_template.cpython-311.pyc` 与 `sandbox_lifecycle_demo.cpython-311.pyc` 已入库，而 `.gitignore` 里已经有 `__pycache__/`——说明是在加 ignore 规则之前提交的。建议 `git rm --cached` 清掉。

### R2-L4 `/healthz` 不鉴权且返回 `replica`

`routes.py:38-40` 返回 `{"ok": True, "replica": <hostname>-<pid>-<随机>}`，向未认证的访问者泄漏内部主机名和进程号。健康检查只需 `ok`；`replica` 可以移到需要鉴权的 `/v1/pool/stats`（那里已经有了）。

### R2-L5 `POST /v1/leases` 无幂等键

调用方在超时后重试会产生两个借用、各占一个沙箱。建议支持 `Idempotency-Key` 请求头，在 `enqueue`/`claim` 的事务内做去重。

### R2-L6 没有「列出 / 强制释放借用」的管理接口

`GET /v1/sandboxes`（`routes.py:116-121`）故意隐藏 `lease_id`——这个决定本身是对的（避免管理员接口泄漏借用凭证）。但结果是：遇到 R2-H1 / R2-M12 这类卡住的借用时，运维除了直连数据库没有别的办法。

**建议**：加 `GET /v1/admin/leases`（管理员，返回 `lease_id` / `client_id` / `state` / `expires_at`）与 `DELETE /v1/admin/leases/{id}`（强制释放）。

### R2-L7 `queue_position` 把 RESUMING 计入可分配数

`repository.py:35` 的 `_AVAILABLE_STATES` 包含 RESUMING（注释解释了原因：要让排在后面的请求算对前面还有多少个沙箱）。副作用是：一个正在被某人恢复的沙箱，同时也被算作其他人的「可分配」，于是 N 个沙箱可能放 N+1 个等待者进来抢。CAS 保证不会双分配，但削弱了 FIFO 准入的精度，也带来无谓的空转轮询。

### R2-L8 429 / 503 不带 `Retry-After`

`app.py:25-35` 的异常处理只返回 `error` / `detail`。`QueueFull`（429）与 `PoolDraining`（503）都应该带上建议的重试时间（前者可用 `wait_timeout_s` 或轮询间隔，后者可用一个保守值），便于调用方实现正确退避。

### R2-L9 `pool_kv.lock` 是单点热行

`repository.py:105-110` 的 `_lock` 被 `reserve_slot`（146）、`start_pause`（319）、`enqueue`（416）共用，每次都是对同一行的 UPDATE。SQLite 下本来就是单写者，无额外代价；但设计文档说「生产可以换 Postgres」，**这将是换库之后的第一个争用点**（所有补货、入队、暂停决策全局串行）。值得在设计文档里先记一笔，或按操作类型拆分锁行。

### R2-L10 对账与 stats 的读放大

`reconcile`（`maintainer.py:407-410`）每周期全表读 `sandboxes` 两次（list 前后各一次，这是正确性要求）；`stats()` 经 `event_durations`（`repository.py:577-591`）每次最多读 5000 行事件。当前规模（5 个沙箱）无感，容量上百、事件累积后需要考虑增量统计或缓存。

### R2-L11 `FakeProvider` 未建模关键的平台语义，导致一整类问题在单元测试里隐形

`provider/fake.py`：

- `warmup`（83-88）与 `run_code`（139-152）**完全不碰 `deadline`**，而真实后端在句柄缓存未命中时会通过 `connect(timeout=...)` 重设平台超时 → R2-M1 无法被测出；
- 没有任何请求超时的概念 → R2-M2 / R2-M10 无法被测出；
- `pause` 不改变 `deadline`，也不模拟「暂停期间 TTL 是否累计」→ R2-L1 无法被测出。

Fake 已经支持 `latency_s` / `kill_latency_s` / `set_timeout_delays` / 多种失败注入，基础设施很好，补上「connect/warmup 重设 deadline」这一条语义即可覆盖 R2-M1 这类回归。

### R2-L12 测试覆盖缺口

除 R2-L11 提到的语义缺失外，以下分支目前没有回归保护：

1. 保活回滚 CAS 失败（R2-H2 的两副本交错）；
2. 非队首等待者遇到排空（R2-M3）；
3. 授予借用后请求被取消（R2-H1）；
4. 无 `Content-Length` 的分块上传（`routes.py:25-36` 的流式计数分支）；
5. warmup 时句柄未命中缓存（R2-M1）。

按 CLAUDE.md 的约定，修这几条时应构造确定性时序，并确认「去掉修复后用例会失败」。

### R2-L13 `_retry_stale` 重试 `create` 仍可能造出重复沙箱

`e2b_provider.py:167-172` 对 `create` 只在 `_NOT_SENT_ERRORS`（`ConnectError` / `WriteError`）时重试，这个判断本身是对的。但 `create` 在服务端是多次 HTTP 调用，**后续调用上的 WriteError 仍可能意味着沙箱已经建好**，重试会造出第二个。由对账作为孤儿清理（`maintainer.py:401-441`），功能上安全，但要花钱。`docs/fc-agent-sandbox-notes.md` 只顺带提了一句，建议在代码注释里也写明这个已知代价。

### R2-L14 后台任务 try 之外的异常要等到停机才被收集

`lifecycle.py:30-45、74-88`：`finish_destroy` 里 `provider.kill` 有 try 保护，但其后的 `delete_sandbox`（83）与 `event`（84-87）没有。若它们抛异常，`spawn` 出去的任务会带着未取回的异常结束，直到 `wait_background`（停机时）才被 `gather` 收集，期间表现为日志里的 "Task exception was never retrieved"。建议给 `spawn` 加一个 `done_callback` 统一记录异常。

## 七、复核确认没有问题的部分

明确列出这些，避免后续重复投入：

1. **不会双分配、不会超容量**。`_cas_sandbox`（`repository.py:200-225`）的 `state` + `version` + `op_owner` + `lease_id` 组合条件覆盖了所有转换路径；`reserve_slot`（139-176）在持池级锁的事务内计数，且**所有状态的记录都计入总数**（包括 DESTROYING），容量是保守的。`test_two_replicas_never_double_allocate_or_exceed_capacity` 与 `test_reserve_slot_never_exceeds_limit_across_engines` 验证到位。
2. **`claim_ready` / `finish_resume` 的三合一事务**（沙箱转 LEASED + 插入借用 + waiter 改 GRANTED）设计正确，因此 `fix_orphan_leased` 没有「LEASED 但借用还没写」的窗口。
3. **崩溃接管闭环完整**。`recover_stuck`（`maintainer.py:117-131`）→ PAUSING/RESUMING 走 `_adopt` 按云端实际状态收回（避免销毁重建，实测节省 3 个沙箱）→ 其余销毁补货；DESTROYING 卡住时重新 CAS 到自己名下重试 kill。端到端两次真实 `kill -9` 验证过。
4. **对账的双读 + 宽限期**（`maintainer.py:401-441`）正确处理了「列表接口有约 1.5s 延迟且默认含已暂停沙箱」这个平台特性：孤儿判断用 list 之后的记录，「已消失」判断只看 list 之前就存在且期间版本未变的记录，再加 `orphan_grace_s`。
5. **`_retry_stale` 的「超时不重试」确实成立**——我核对了 httpx 的异常继承关系，`TimeoutException` 与 `NetworkError` 互不包含，所以 `retry_on=_STALE_CONNECTION_ERRORS` 不会把超时也算进去，调用耗时不会突破过渡态截止时间。
6. **`pause` 的「重试失败后以云端实际状态为准」**（`e2b_provider.py:181-200`）逻辑正确：用 `stale` 标志区分「请求可能已送达」与「确定没送达」，只在前者且实际已 paused 时吞掉异常。
7. **`_on_create_failed` 的分步保护**（`maintainer.py:363-392`）顺序正确：**先累加熔断计数再释放名额**，熔断在名额释放前生效，补货不会在两步之间又发起新创建；每一步独立 try，任何一步失败都不影响后面（尤其是释放容量）。
8. **优雅停机**（`maintainer.py:51-68`、`allocator.py:64-66`）用「事件通知 + 等待」而非直接 cancel 正在做数据库操作的协程，符合 CLAUDE.md 的约束。
9. **轻量迁移**（`repository.py:42-62`）只做「新增可空列 / 索引」，遇到 NOT NULL 缺列时明确抛错要求手工迁移；`init_schema` 对多副本并发建表做了 3 次重试。
10. **鉴权实现细节正确**：`identify`（`auth.py:61-70`）逐个常量时间比较且不提前返回；同一 key 同时配在两类里时按管理员算；`Caller.owner`（`auth.py:24-27`）用 `None` 表示管理员不受限，与 allocator 的 `owner` 语义一致；`insecure_bind`（`__main__.py:13-19`）对 IP 与主机名两种情况都做了判断。
11. **SQLite 连接策略**（`db.py`）与文档一致：写引擎 `pool_size=1, max_overflow=0` + `BEGIN IMMEDIATE`；只读引擎 `pool_size=4` + 普通 `BEGIN` + `PRAGMA query_only=ON`；非 SQLite 后端读写共用普通连接池。
