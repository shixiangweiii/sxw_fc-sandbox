## 1. 结论

1. **可行**：pi 内置 DeepSeek（`deepseek/deepseek-flash`，与现在的模型 ID 相同），凭证读 `DEEPSEEK_API_KEY`，现有「占位符 + 平台出网注入」可以直接沿用。
2. **pi 没有可用的网络服务模式**，需要自建桥接进程：
   - pi 的稳定接入方式只有两种：SDK（进程内 TypeScript）和 RPC（stdin/stdout 上的 JSONL，一个进程一个活动会话）；
   - 仓库里的 `pi-server` 标注 experimental，走 Unix socket + CBOR，没有鉴权，不能用。
   - 沙箱里要放一个小的桥接进程，对网关提供与 opencode 同构的 HTTP/SSE 接口。
3. **推荐方案**：
   - 桥接进程为每个会话起一个 `pi --mode rpc` 子进程，自身只做协议转发和进程管理，保持很薄（改桥接进程要重建模板）；
   - 事件翻译、结果提取放在网关侧 Python 代码里；
   - 网关抽出「引擎」接口，opencode 和 pi 各一个实现；
   - 引擎按 agent 选择，每个引擎一个模板。**切换引擎等于换沙箱**，复用现有的轮换机制。
4. **对外接口基本不变**：
   - SSE 事件（`start / text / reasoning / tool / status / done`）、任务、定时任务、出网策略的语义都不变；
   - 新增的只有设置项 `engine`、查询引擎列表的接口、沙箱视图里的 `engine` 字段。
5. **主要收益**：
   - 内存：pi 的 RPC 进程约 113MB（本机实测），opencode 约 850MB，模板有望从 2C4G 降到 2C2G；
   - 重载配置不必中止运行中的会话；
   - 会话是纯 JSONL 文件，以后可以在沙箱轮换时迁移会话。
6. **主要代价与风险**：
   - pi 仍是 0.x，SDK 几乎每个小版本都有 breaking change，必须锁版本；RPC 线协议相对稳定；
   - 没有内置 MCP 和联网搜索，要靠第三方扩展 `pi-mcp-adapter`，或自写一个小工具；
   - 没有权限系统，沙箱就是边界。这与 opencode 的现有配置等价；
   - 以上都需要一轮云上 PoC 确认（第 7 节）。

## 2. pi 是什么

**项目**：
- Earendil Inc. 维护，MIT 协议，monorepo `earendil-works/pi`；
- 核心包：
  - `@earendil-works/pi-coding-agent`：CLI 与 SDK；
  - `pi-agent-core`：agent 运行时；
  - `pi-ai`：多模型统一接口。
- 当前版本 0.87.1（2026-09-22）。发版很密：0.86.0（09-19）和 0.87.0（09-21）都带 Breaking Changes。

**运行方式**（`docs/cli-integration.md`、`docs/rpc.md`）：

| 方式 | 形态 | 适用 |
| --- | --- | --- |
| Interactive | 终端 UI | 人用 |
| Print / JSON | 一次调用，跑完退出；JSON 模式输出 JSONL 事件 | 脚本、一次性任务 |
| **RPC** | 常驻子进程，stdin 收 JSONL 命令，stdout 出响应和事件；**一个进程一个活动会话**（`new_session` / `switch_session` 会替换它） | 其他语言接入、进程隔离 |
| **SDK** | `createAgentSession()`，进程内多个 `AgentSession` | Node / Bun 宿主 |
| pi-server | experimental；Unix socket + CBOR，鉴权由应用自理 | 不适用 |

**RPC 协议要点**：
- `prompt` 的成功响应只代表已受理（`disposition: started | queued | handled`）；
- 会话正在运行时再发 `prompt` 必须指定 `streamingBehavior`，否则报错；
- `abort` 会等会话回到空闲后才响应；
- 完成判定看 `agent_settled`，而不是 `agent_end`：`agent_end` 之后还可能有自动重试、上下文溢出恢复、压缩、排队消息；
- `get_state` 返回 `isStreaming / sessionId / sessionFile`；
- `get_messages` 返回完整消息；`get_session_stats` 返回 tokens 与 cost；
- 分帧只能按 LF 切：Node `readline` 会把 U+2028 / U+2029 当换行，不能用；stdout 必须持续读，否则 pi 会被背压卡住；
- 关闭 stdin 即有序退出，退出前销毁运行时，也就是会中止运行中的会话。

**事件**（`docs/json.md`，RPC 与 JSON 模式共用）：
- 生命周期：`agent_start / turn_start / message_start / message_end / turn_end / agent_end / agent_settled`；
- 消息增量：`message_update.assistantMessageEvent` 的 `text_* / thinking_* / toolcall_*`，线上只有增量；
- 工具：`tool_execution_start / update / end`（`toolCallId`、`args`、`result`、`isError`）；
- 其他：`auto_retry_start / end`、`compaction_start / end`、`queue_update`、`extension_error`。

**模型与凭证**：
- `providers.md` 列出 DeepSeek，环境变量 `DEEPSEEK_API_KEY`；
- `pi-ai` 的 DeepSeek provider：`baseUrl=https://api.deepseek.com`，走 openai-completions 接口（HTTP SSE）；
- 模型目录里有 `deepseek-flash`（DeepSeek V4.1 Flash，1M 上下文）和 `deepseek-v4-pro`。

**工具与扩展**：
- 内置工具默认 `read / bash / edit / write`，另有 `grep / find / ls`；**没有 webfetch / websearch**；
- **不内置 MCP**（设计如此），扩展是进程内加载的 TypeScript 模块，包通过 npm / git 分发；
- 相关第三方包：
  - `pi-mcp-adapter`（约 100 万次/月）：支持远程 StreamableHTTP 和自定义请求头，默认懒连接，也支持在代码中直接传入配置；
  - `pi-web-access`：搜索、抓取。

**安全模型**（`docs/security.md`）：
- 没有权限系统，以启动用户的权限执行，不逐次询问；官方建议整个 pi 进程跑在容器 / 虚拟机 / 沙箱里；
- 「项目信任」只控制是否加载 `.pi/` 下的设置和扩展。`AGENTS.md` / `CLAUDE.md` 不受项目信任控制，总会加载；
- RPC / Print 模式没有信任提示，按 `defaultProjectTrust` 或 `--approve` 决定。

**会话与上下文**：
- 会话是树结构的 JSONL，默认在 `~/.pi/agent/sessions/`，按工作目录分组；可用 `--session-dir` 或 `PI_CODING_AGENT_SESSION_DIR` 改位置，用 `--session <路径或 ID>` 打开；
- 接近上下文上限时自动压缩；自带 agent 级重试（`retry.*`）。

**配置与环境变量**：
- 目录：`~/.pi/agent/`（可用 `PI_CODING_AGENT_DIR` 改），包含 `settings.json`、`models.json`、`auth.json`、`AGENTS.md`；
- 无人值守相关：`PI_OFFLINE=1`（关闭自动联网，含模型目录刷新）、`PI_SKIP_VERSION_CHECK=1`、`PI_TELEMETRY=0`；
- 设置项：`transport`（`auto / sse / websocket`）、`httpIdleTimeoutMs`、`defaultProvider / defaultModel / defaultThinkingLevel`。

**分发**：
- npm 包要求 **Node ≥ 22.19**；
- GitHub Release 有 Bun 编译的单文件二进制（`pi-linux-x64.tar.gz`），不依赖 Node。

## 3. 本机实测（2026-09-26，macOS arm64，Node 24.19，pi 0.87.1，零成本）

用 pi 自带的 faux 模型（不访问任何模型服务）和 SDK / RPC 做了几项验证。脚本在 `/tmp/pi-exp/`，没有入库。

| 验证项 | 结果 |
| --- | --- |
| SDK：同一进程两个会话并发（A 跑 2s 的 bash 工具，B 普通对话） | ✅ 并发执行，2.4s 全部完成；进程 RSS 约 125～130MB |
| 事件序列 | `agent_start > turn_start > message_end:system > message_end:user > thinking_* > toolcall_* > message_end:assistant/toolUse > tool_execution_* > message_end:toolResult > turn_end > turn_start > text_* > message_end:assistant/stop > turn_end > agent_end > agent_settled` |
| 消息角色 | 0.87 起每个会话开头多一条 `role=system`（带分段的系统提示词）；提取结果时要跳过 |
| 用量 | 每条 assistant 消息带 `usage {input, output, cacheRead, cacheWrite, totalTokens, cost.total}`，没有单独的 reasoning tokens |
| 工具执行中 `abort()` | 会话回到空闲；最后一条 assistant 的 `stopReason=error`、`errorMessage="This operation was aborted"`（faux 下的表现，真实 provider 待 PoC）。**网关不能靠 stopReason 判断中止**，要用自己的中止标记（现有 runner 就是这样） |
| 模型报错 | `stopReason=error` + `errorMessage`，事件流仍以 `agent_settled` 结束 |
| 会话落盘后重开 | ✅ `SessionManager.open(文件)` 恢复全部 5 条消息 |
| **`session.reload()`** | ⚠️ 会调用进程级的 `resetApiProviders()`：清空并重注册内置 provider，运行中调用会让该会话下一轮报错，**同进程其他会话**也受影响。DeepSeek 是内置 provider，影响可能较小；扩展注册的 provider 会丢失。结论：不在多会话进程里用 `reload()` |
| RPC 模式冷启动 | `pi --mode rpc --no-session --provider deepseek --model deepseek-flash` 到 `get_state` 响应 0.57s（3 次一致），RSS 约 113MB，`get_state` 回显 DeepSeek 模型与 openai-completions 接口 |
| npm 包 | `@earendil-works/pi-coding-agent` 带 shrinkwrap，自带一份嵌套的 `pi-ai`。宿主或扩展另装的 `pi-ai` 是另一份实例，注册表不共享（实测 faux provider 必须从嵌套那份注册）。安装后 `node_modules` 约 524MB（macOS，含平台二进制） |

## 4. 与 opencode 的对照

| 维度 | opencode（现状） | pi |
| --- | --- | --- |
| 对外协议 | 自带 HTTP server（`opencode serve`），全局 SSE `/event` | 无网络服务；RPC（stdio JSONL）或 SDK，**需要桥接进程** |
| 多会话 | 一个进程多个会话 | RPC：一进程一会话；SDK：一进程多会话 |
| 完成判定 | `session.status` 从 busy 回到 idle | `agent_settled` |
| 中止 | `POST /session/{id}/abort` | RPC `abort`（等会话空闲后才响应） |
| 配置重载 | `POST /instance/dispose`，**会中止所有运行中的会话**（AG-H2） | RPC：重启该会话的进程（空闲时）；SDK 的 `reload()` 有进程级副作用 |
| 权限询问 | 有，需要自动拒绝（`permission.asked` / `question.asked`） | 没有权限系统；只有扩展可能通过 extension UI 提问 |
| MCP | 内置（`opencode.json` 的 `mcp` 段） | 不内置，依赖 `pi-mcp-adapter`（第三方） |
| 网页工具 | 内置 webfetch | 无，用 bash + curl，或装扩展 |
| 子 agent / 模式 | 内置 agent（build / plan），接口的 `agent` 参数 | 无内置，靠扩展 |
| 内存 | 约 850MB（模板 2C4G） | RPC 进程约 113MB（本机） |
| 会话存储 | opencode 自己的存储 | 纯 JSONL 文件，便于拷贝迁移 |
| 版本节奏 | 模板锁 1.18.32 | 0.x，发版密、SDK 常有破坏性变更，必须锁版本 |

## 5. 沙箱内部署方案

### 5.1 选型：pi 怎么接到网关

| 方案 | 做法 | 评价 |
| --- | --- | --- |
| **A. 桥接进程 + 每会话一个 RPC 子进程（推荐）** | 沙箱内常驻一个桥接进程（HTTP/SSE），每个活动会话 spawn 一个 `pi --mode rpc --session <文件>`；空闲一段时间回收进程，下次按会话文件重开（约 0.6s） | 用官方为「其他语言、进程隔离」推荐的接口，线协议比 SDK 稳定；会话之间隔离，一个会话的中止、崩溃、重载不影响其他会话；重载就是重启空闲会话的进程，没有 `reload()` 的全局副作用。代价：每个活动会话约 110MB，桥接进程要管进程生命周期 |
| B. 桥接进程内嵌 SDK | 一个 Node 进程持有多个 `AgentSession` | 最省内存、控制最细（自定义工具、内存设置、ResourceLoader）。但 SDK 破坏性变更多，升级要改桥接代码；进程级状态共享（`reload()`、一处崩溃影响全部会话）。可作为 A 的备选 |
| C. 网关经 envd 直接驱动 `pi --mode rpc` 的 stdin/stdout | 不需要桥接进程 | 不采用：输出流绑定在某个网关副本的长连接上，副本崩溃后接管困难；本机代理环境下 envd 连接不稳定（`CLAUDE.md` 已记录）；平台 envd 是重新实现的，stdin 支持程度未知 |
| D. `pi-server` | 官方实验性服务 | 不采用：experimental，Unix socket + CBOR，无鉴权 |

**桥接进程保持薄**：只做协议转发（HTTP/SSE ↔ JSONL）、会话 ↔ 进程映射、运行状态记录。事件翻译和结果提取放在网关 Python 代码里。
- 理由：桥接进程打在模板里，改它要重建模板；网关代码按常规发布，并且有现成的单测和多副本测试设施。
- 语言：建议 Node 零依赖单文件（pi 本身就要 Node，分帧与背压的坑都在 Node 生态）。也可以用 Python 标准库实现。

### 5.2 桥接进程接口（草案，尽量与 opencode 的用法同构）

| 接口 | 说明 | 对应 pi |
| --- | --- | --- |
| `GET /health` | `{healthy, engine: "pi", pi_version, bridge_version}` | — |
| `POST /session` | 新建会话，返回 `{id}` | spawn `pi --mode rpc --session-dir …`，再 `get_state` 取 `sessionId / sessionFile` |
| `POST /session/{id}/prompt_async` | `{text, model?}`，返回 `{run_id}`；会话忙返回 409 | RPC `prompt` |
| `POST /session/{id}/abort` | 幂等 | RPC `abort` |
| `GET /session/status` | `{session_id: {type: busy, run_id}}`，空闲的不列出 | 桥接进程维护：从受理到 `agent_settled` 记为 busy |
| `GET /session/{id}/runs/{run_id}` | `{state: running / settled / lost}`；`lost` 表示桥接进程或会话进程重启过、这次运行已不存在 | 桥接进程维护 |
| `GET /session/{id}/message` | pi 的原始消息列表 | RPC `get_messages`；进程已回收时读 JSONL |
| `GET /event` | 全局 SSE：第一条 `{"type":"server.connected"}`，之后每条为 `{session_id, run_id, event: <pi 原始事件>}`，定期发心跳注释 | 各会话进程 stdout 的汇总 |
| `POST /instance/reload` | 重启所有空闲会话的进程，使新配置生效；忙的会话返回在 `deferred` 里 | 重启进程 |

几点设计：
- **`run_id` 用来区分「正常结束」和「进程丢了」**：
  - 现在 opencode 的 runner 靠「会话不在忙碌列表」判完成，进程重启后可能把残缺结果记为 `SUCCEEDED`。AG-L6 是同类问题；
  - 桥接进程重启后旧 `run_id` 查不到，返回 `lost`，网关记为 `FAILED`。
- **extension UI 请求**：扩展（例如 MCP 适配器）可能通过 RPC 发出 `extension_ui_request`。桥接进程按白名单自动应答，其余拒绝，并作为事件上报。对应 opencode 的自动拒绝询问。
- **并发上限**：桥接进程限制同时存活的会话进程数，超出时回收最久未用的空闲进程。网关的 `agent_max_running_tasks` 仍是准入的权威限制。

### 5.3 模板

在 `scripts/build_opencode_template.py` 的基础上新建 pi 模板（或把脚本改成按引擎参数化）：
- 基础镜像沿用官方 code-interpreter（第二代）。**官方模板已配置平台 CA**，文档写明 curl、Python requests、Node.js 可以开箱通过出网注入的 TLS 检查。
- **Node 版本需核实**：pi 要求 Node ≥ 22.19。镜像自带的 Node 不够新时，从 npmmirror 的 Node 二进制镜像装 Node 24。备选：从 GitHub Release 取 Bun 单文件二进制（构建期访问 GitHub 可能不稳，需要转存）。
- 安装：
  - 从 npm 国内镜像安装 `@earendil-works/pi-coding-agent@0.87.1`、`pi-mcp-adapter`，均锁定版本；
  - 写入桥接进程和守护循环 `run.sh`，与 opencode 模板一样在构建期启动，打进快照。
- 环境变量：`PI_OFFLINE=1`、`PI_SKIP_VERSION_CHECK=1`、`PI_TELEMETRY=0`、`DEEPSEEK_API_KEY=injected-by-platform`。
- 规格：先按 2C2G 做 PoC，看真实模型 + MCP 下的内存再定。

### 5.4 出网与凭证

完全复用 `agent/policy.py` 的策略与注入，与引擎无关。需要注意：
- 平台注入**不支持 WebSocket / HTTP Upgrade**（fc-docs《出网请求头转换》）。pi 设置里固定 `transport: "sse"`；DeepSeek 本来就走 HTTP SSE，这里只是防御。
- `PI_OFFLINE=1` 避免 pi 在白名单模式下访问 `pi.dev` 或模型目录时卡住。

### 5.5 设置项映射（网关 → 沙箱文件）

| 网关设置 | opencode（现状） | pi |
| --- | --- | --- |
| 模型 | `opencode.json` 的 `model` | `~/.pi/agent/settings.json` 的 `defaultProvider / defaultModel`，或启动参数 `--provider / --model` |
| `instructions` 与运行环境说明 | 工作目录 `AGENTS.md` | 同一个 `AGENTS.md`（pi 从工作目录读，不受项目信任影响），工具提示按引擎改写 |
| `mcp` | `opencode.json` 的 `mcp` 段 | 工作目录 `.mcp.json`（`pi-mcp-adapter` 格式：remote 转为 `{url, headers}`，local 转为 `{command, args, env}`） |
| 出网策略 | `~/.agent/egress.json` | 相同 |
| 生效方式 | 写文件 + `dispose`（中止全部运行中会话，需要与准入互斥） | 写文件 + `/instance/reload`（只重启空闲会话进程）。现有的 `begin_reload` 互斥照样保留，对两种引擎都成立 |

## 6. 结合现有代码的改造评估

### 6.1 现在与 opencode 绑定的地方

| 位置 | 内容 |
| --- | --- |
| `agent/opencode.py` | HTTP 客户端与 `OpencodeAPI` 协议。协议本身接近通用；`reply_permission / reject_question` 是 opencode 特有的 |

### 6.2 网关侧的引擎抽象

新增 `agent/engines/`，每个引擎提供：

```python
class AgentEngine(Protocol):
    name: str                    # "opencode" | "pi"
    template: str; port: int; model: str
    capabilities: dict           # 例如 {"agent_param": False, "reload_aborts_running": False}
    def client(self, endpoint, access_token, *, ingress_ip) -> EngineClient: ...
    def translator(self, session_id: str) -> Translator: ...          # feed(ev) -> [(kind, data)]，暴露 idle / errors / asks
    def extract_result(self, messages: list[dict]) -> tuple[str, dict, Optional[str]]: ...
    def render_files(self, ctx) -> dict[str, bytes]: ...              # opencode.json 或 settings.json / .mcp.json，以及 AGENTS.md
    def validate_message(self, agent_name: Optional[str]) -> None: ...  # pi 不支持 agent 参数时返回 400
```

- `EngineClient` 就是现在的 `OpencodeAPI`：
  - `dispose` 改名为 `reload`；
  - 询问的应答收敛为 `answer_ask(kind, id)`；
  - 增加可选的 `run_state(session_id, run_id)`。
- 第一步只把 opencode 现有代码搬到 `OpencodeEngine` 后面，**行为零变化**，现有 147 个单测应全部原样通过；第二步再加 `PiEngine`。
- runner、service、maintainer 统一通过 `svc.engine_for(row)` 拿到引擎。沙箱行上记录引擎，接管、断线重连、健康检查都按沙箱行找引擎，不看 agent 当前的设置。

### 6.3 引擎选择的语义

**粒度：按 agent 选择（推荐）**。
- 设置里新增 `engine`，通过 `PATCH /v1/agents/{user_id}/settings {"engine": "pi"}` 设置；
- 没设置时用 `POOL_AGENT_DEFAULT_ENGINE`（默认 `opencode`，老 agent 行为不变）。

**切换引擎等于换沙箱**，复用轮换逻辑：
- `sandbox_for`（`service.py:254`）：ACTIVE 沙箱的引擎与设置不一致时，与「剩余寿命不足」一样 CAS 为 RETIRING，然后新建沙箱；
- 维护循环 `check_sandbox`（`maintainer.py:159` 附近，与 `rotate_after` 并列）：引擎不一致时，没有运行中任务就销毁，有就 RETIRING；
- 运行中的任务在旧沙箱上跑完；新消息进新引擎；
- 旧会话不能续聊，返回 409 并提示新开会话。这与沙箱被轮换后的现有行为一致。定时任务照常，下次触发时用新引擎。

**不推荐按消息或按会话选引擎**：那需要一个模板同时跑两套引擎。
- opencode 常驻约 850MB，两套一起对内存不友好，升级也互相牵连；
- 同一个 agent 的上下文分裂在两个引擎里，语义也别扭。

### 6.4 数据、配置与接口改动

- **表结构**（只加可空列，符合 `_migrate` 约束）：`sandboxes.engine`，NULL 视为 `opencode`。agent 的引擎存在 `agents.settings` JSON 里，不加列。
- **配置**：新增 `POOL_AGENT_ENGINES`，JSON 格式 `{引擎: {template, port, model}}`，另加 `POOL_AGENT_DEFAULT_ENGINE`。没配 `POOL_AGENT_ENGINES` 时，由现有的 `POOL_AGENT_TEMPLATE / PORT / MODEL` 推出只有 opencode 的配置，老部署不用改。
- **接口**：
  - `GET /v1/agents/engines`：列出已启用的引擎及能力差异，供接入方选择；
  - `GET /v1/agents/{user_id}`：返回当前引擎；沙箱视图带 `engine`；
  - `POST …/messages` 的 `agent` 参数：引擎不支持时返回 400，不静默忽略。
- **对外事件**：结构不变，个别字段按引擎可能为空：
  - pi 的 `tool` 事件没有 `title`；
  - `usage.reasoning` 为 0；
  - 工具名是引擎原生的，例如 pi 的 `bash` / `read`，opencode 的 `webfetch`。

  手册要写明这些差异。
- **定时任务**、**出网策略**：接口与语义不变。

### 6.5 测试

- 新增 `provider/fake_pi.py`：内存版桥接进程，模拟 pi 的事件序列（参照第 3 节实测）。用 `[sleep:秒]`、`[tool]`、`[error]` 这类指令驱动，与 `FakeOpencode` 的用法一致。以下两点要与真实行为保持一致：
  - 进程丢失后运行记录变为 `lost`；
  - 重载不影响运行中的会话。
- 现有用例保持对 opencode 引擎运行。service 和 api 层的关键用例按引擎参数化：首轮建沙箱、会话连续、中止、超时、接管、断线重连、定时任务。
- 新增引擎切换用例：有运行中任务时切换，旧任务跑完、新消息进新沙箱、旧会话返回 409；两个副本并发切换时只建一个新沙箱。
- 桥接进程自带测试（`node:test`），用一个假的 `pi --mode rpc` 脚本覆盖：分帧（含 U+2028）、背压、进程崩溃后 `lost`、空闲回收后重开。
- 端到端：S1–S11 按引擎各跑一遍，另加一个切换引擎的场景。

## 7. 风险与需要 PoC 确认的事项

需要一轮云上 PoC（临时沙箱，结束后销毁），逐项确认：

| # | 事项 | 不成立时的对策 |
| --- | --- | --- |
| P1 | code-interpreter 镜像的 Node 版本；装 Node 24 后，Node 通过平台 CA 做 TLS 检查、DeepSeek 占位符被注入覆盖 | 设 `NODE_EXTRA_CA_CERTS=/usr/local/share/ca-certificates/e2b-ca.crt`；或改用 Bun 单文件二进制（opencode 同为 Bun，已验证可行） |
| P2 | pi 调真实 DeepSeek：流式、工具调用、`abort` 后的 `stopReason`、usage / cost 字段 | 在网关侧的结果提取里适配 |
| P3 | `pi-mcp-adapter` 在 RPC 模式下连百炼 WebSearch MCP：请求头注入、懒连接、是否弹出需要应答的确认；工具是直接暴露还是走代理工具 | 自写一个只接百炼 WebSearch 的小扩展（几十行），不依赖第三方包 |
| P4 | 桥接进程的 SSE 经平台入口长时间保持（opencode 已验证 150s 空闲不断） | 与 opencode 相同：runner 断线重连 + 状态轮询 |
| P5 | 真实负载下的内存：3 个并发会话 + MCP | 调模板规格或并发上限 |
| P6 | 新会话在第一条消息之前是否落盘（影响空闲回收后能否重开） | 桥接进程延迟到第一条 `prompt` 再 spawn |
| P7 | 构建期从 npm 国内镜像安装的耗时与体积（本机 `node_modules` 约 524MB） | 只装 linux-x64 依赖、`--omit=optional` 精简 |

长期风险：
- **上游节奏**：pi 0.x 发版密，破坏性变更多。对策：
  - 锁版本；
  - 升级走「模板新版本 + 灰度切换」，旧沙箱随轮换自然退役；
  - 桥接进程只依赖 RPC 线协议，不依赖 SDK 类型。
- **第三方扩展**：`pi-mcp-adapter` 对 `pi-ai` 有 peer 版本范围（当前 `^0.84 ~ ^0.87`），pi 升级时可能不兼容，要一起锁版本、一起验证。
- **能力差异**：pi 没有 opencode 的 plan / build agent、内置 webfetch、权限询问。接入方选 pi 前要知道这些差异，`GET /v1/agents/engines` 和手册负责说明。

## 9. 待决策的问题

1. **选择粒度**：按 agent 选择、切换即换沙箱（推荐），还是需要按消息 / 会话选择（需要双引擎模板）？
2. **谁能选**：所有调用方都能在已启用的引擎中自选（推荐），还是由管理员按调用方指定？
3. **桥接方式**：每会话一个 RPC 进程（推荐），还是单进程 SDK？
4. **pi 的联网搜索与 MCP**：用第三方 `pi-mcp-adapter`（通用，但有版本耦合），还是自写只接百炼 WebSearch 的小扩展（可控，但只支持这一个 MCP）？建议先按前者做 PoC，失败再退到后者。
5. **能力差异是否可以接受**：pi 不支持 `agent` 参数、没有内置 webfetch（agent 会用 curl）。
6. **模型**：两种引擎默认都用 `deepseek/deepseek-flash`；是否需要按引擎或按 agent 配置模型？
7. **（遗留）订阅规格**：Team 的 `plan` 实测是 `pro`，与 Eco 前提不一致。如果确认是 Pro，沙箱最长存活和能否休眠会变，可能影响两种引擎的轮换参数。
